## 5. 腕の制御方式：2つの経路を両方用意する

### プランA：`rt/arm_sdk`（第一候補）
- 下半身は内蔵の歩行コントローラにバランスを任せ、**腕だけを `rt/arm_sdk` で PD 指令する**。指令は、コントローラの出力に weight（`motor_cmd[29].q`、0.0〜1.0）でブレンドされる。
- **デバッグモードには入らない**（内蔵コントローラが止まり、arm_sdk の受け手がいなくなる）。
- 公式の参考：unitree_sdk2 / unitree_sdk2_python の `example/g1/high_level/` にある arm_sdk の例、公式 `xr_teleoperate`。

### ⚠️ arm_sdk が効かないリスク
`Dev/Navigation` ブランチの `Teleop/vendor/g1-starter-kit/`（外部の開発者のキットを取り込んだもの）に、次の記録がある。
- その開発者の G1（29DoF、Regular モード）では、arm_sdk の weight を 1.0 にしても腕が **0.000 rad** しか動かなかった。
- **チームの機体で確認されたわけではない**ので、実機日に最初に確認する。

### プランB：デバッグモード＋`rt/lowcmd`
- arm_sdk が効かない場合の経路。**座った状態（椅子）または吊り下げ状態で行う**（バランス制御が止まるため）。
- 腕だけでなく全関節に指令を送る必要がある。腕以外の関節（脚・腰）には、開始時の姿勢を保持する指令を低めのゲインで送り続ける。
- デバッグモードでは内蔵コントローラと競合しないが、重力補償もないので、Kp が低すぎると腕が落ちる。

### 共通の落とし穴（g1-starter-kit の記録より）
- ロボットがゼロトルク（FSM 0）状態だと、`rt/lowstate` の `motor_state[].mode` が `0` になり、**送信は成功と表示されるのに何も動かない**。リモコンでダンピング（FSM 1）に入れて有効化する。有効化は、指令の `motor_cmd[].mode = 1` ではできない。
- プログラムを終了するたびにゼロトルクに戻ることがある。毎回、実行前に `mode` を確認する。
- 送信する指令の `mode_machine` は、lowstate の値と一致させる。
- どちらの経路でも「エラーなしで動かない」という失敗が起きるので、**送信後に lowstate の関節角が実際に変わったかを必ず確認する**。

### 流用できる既存ツール（`Dev/Navigation` ブランチの `Teleop/vendor/g1-starter-kit/tools/`）
| ツール | 用途 |
|---|---|
| `mode_check.py` | モーションコントローラの状態と、どちらの経路が効くかを判定する。デバッグ状態への切り替え（`--release` / `--restore`）もできる |
| `armsdk_probe.py` | arm_sdk が効くかを、関節を3°だけ動かして確かめる |
| `cmd_monitor.py` | arm_sdk / lowcmd の受信数、weight、実際の移動量を監視する |
| `replay_arm.py` | 腕の姿勢を記録・再生する（ティーチングに流用できる）。腕関節のインデックス対応、weight の扱い、実績のあるゲインが参考になる |

### 必須の安全要件
1. **weight を急に切り替えない**（プランA）。開始時は、現在の関節角を読んで目標値にし、その姿勢を保ったまま weight を 0→1 にゆっくり上げる。終了時は 1→0 にゆっくり下げる。
2. arm_sdk にはウォッチドッグがなく、プロセスが落ちると最後の目標を保持し続ける可能性がある。そのため、**SIGINT / SIGTERM / 例外のすべてで安全に終了する処理**（プランAなら weight を下げる、プランBなら現在の姿勢を保持してから停止する）を入れる。
3. 関節リミットを確認し、1ステップあたりの関節の最大移動量を制限する。手先が作業空間（箱）の外に出る目標は拒否する。
4. IK が収束しない、または関節リミットに当たる場合は「届かない」として動かない。
5. **dry-run モード**（計算して表示するだけで送信しない）と、**確認モード**（各段階で Enter を待つ）を用意する。
6. 腰の関節は動かさない。腰 3DoF の機体では、腕を動かすと前傾してバランスを崩すという報告がある。
7. 緊急停止はリモコンの L2+B（ダンピング）。人が常にリモコンを持っておく。

## 6. 技術的な方針

### PD 制御と押す力
- 各関節のトルクは `τ = Kp(q_目標 − q) + Kd(dq_目標 − dq) + τ_ff` で決まる。
- 押す力は、目標をどれだけ奥に置くかと Kp で決まる。見積もりは `τ = Jᵀ F` を使う。例：肩から0.4m、10N で押す → 4Nm 必要。Kp=40 なら 0.1rad、つまり手先で約4cm奥に目標を置く。
- 押し込みの深さには上限を設ける。空振りしたときに腕が勢いよく伸びるのを防ぐため。
- ボトルは柔らかいので、**Kp は低め、押し込みは浅め（1〜2cm）**で十分。

### IK
- URDF と Pinocchio（または同等のライブラリ）で FK と IK を行う。
- 記録した押し込み姿勢 `q_rec` を初期値にして、微分 IK（`Δq = J⁺ Δx`、ダンピング付きの擬似逆行列を推奨）を反復する。対象は片腕の7関節（腰は固定）。
- 位置のずれは、肩だけで補正しない。円弧を描いて指の向きがずれるため。IK で肩・肘・手首を協調させる。
- 動作は2段階に分ける：
  1. 対象の法線方向に約5cm手前の姿勢まで、**関節空間で補間**して移動する。
  2. そこから法線に沿って手先を**直線で**押し込み、戻る。直線上の点ごとに IK を解く。
- 補間は `s = 3t² − 2t³` を使う（始点と終点で速度0になる）。送信は50〜100Hz 程度。

### 認識と座標変換
- 事前学習済みの YOLO で `bottle` を検出する。**`Perception/common/` の既存の `YoloDetector` と `ZmqFrameSource` を再利用する**（MuJoCo の `head_camera` も同じ ZMQ の仕組みで配信されている）。
- **透明な PET ボトルは深度が取れない**（赤外線が透過するため）。ラベル付きのボトルを使い、深度はバウンディングボックス中央付近の領域から、無効値を除いた中央値で取る。
- カラー画像に位置合わせした深度と、カメラの内部パラメータからカメラ座標を求め、URDF の頭カメラの取り付け位置（と腰の関節角）を使って胴体座標に変換する。
- 当日、既知の位置に置いた対象で較正し、一定のずれがあれば補正値として設定ファイルに入れる。

## 7. 実装タスク（この順番で）

各タスクで、単体テストまたは MuJoCo での確認方法も一緒に用意すること。

| # | タスク | 完了の条件 |
|---|---|---|
| 1 | **腕の指令部分をまとめる**（`send_arm_cmd` 相当）。**シミュレーション／プランA（arm_sdk）／プランB（デバッグ＋lowcmd）の3つを切り替えられる**ようにし、5章の安全要件 1〜5 をここに実装する。送信後に lowstate で実際に動いたかを確認する機能も付ける | MuJoCo 上で、指定した関節角へ安全に動く。Ctrl+C で安全に止まる |
| 2 | **FK / IK と軌道生成**（手前の姿勢への移動、直線の押し込み） | MuJoCo 上で、目標座標に手先が届く（誤差 1cm 以内程度）。届かない目標を拒否できる |
| 3 | **深度付きストリーム**。既存の ZMQ サーバとクライアントを拡張し、位置合わせした深度（16bit、JPEG にはしない）とカメラの内部パラメータを配信する。既存の RGB クライアントとの互換性は保つ | 実機がなくても、ダミーデータで送受信テストが通る |
| 4 | **ボトル検出 → 3D 座標 → 胴体座標** | 写真や録画データでボトルの座標が出る。MuJoCo のカメラで座標変換が確認できる |
| 5 | **収録ツール**。RGB、深度、lowstate（関節角）を時刻付きで保存する。ボタン撮影用に、間引き保存モードも付ける | 保存したデータを再生して、オフラインで4を実行できる |
| 6 | **全体をつなぐスクリプト**（検出 → 目標 → IK → 手前の姿勢 → 押し込み → 戻る）。dry-run モードと確認モードを付ける | MuJoCo 上で一連の流れが動く |
| 7 | **当日用のツール**：関節角の記録（ティーチング。`replay_arm.py` の流用を検討）、FK の確認、較正用のスクリプト | 下の当日手順どおりに実行できる |

- パラメータ（経路 A/B、Kp/Kd、押し込みの深さ、手前の距離、較正値、作業空間、URDF のパスなど）は、すべて設定ファイル（YAML など）に出す。当日はコードを編集しなくて済むようにする。
- 既存の g1-starter-kit のツールは、コピーして書き換えるのではなく、なるべくそのまま呼び出すか、参考にして書く（取り込み元の方針は `UPSTREAM.md` を参照）。

**MuJoCo について：** unitree_mujoco は SDK2 と同じ DDS で通信できるが、**低レベル（LowCmd / LowState）のみ対応**で、内蔵の歩行コントローラはない（Navigation の調査で確定済み）。そのため arm_sdk のブレンド動作は再現できない。シミュレーションでは、胴体を固定して腕の IK と軌道を検証すれば十分。

## 8. 実機日の手順

| 段階 | 内容 | 失敗したときの対応 |
|---|---|---|

| 3 | 押し込み姿勢をティーチングで記録し、FK と実測を比べる | URDF と関節の対応を確認する |

## 9. 未確認事項（推測で決めずに確認すること）

- **チームの機体で arm_sdk が効くか**（当日の段階2で確認）。
- 座った状態で arm_sdk が効くか（公式の使い方は立った状態）。
- 深度をどこで取得するか（PC2 に接続された RealSense か。ロットによっては PC1 側に接続されているので、PC2 で `lsusb` を確認する）。

## 10. その後（10/1〜13）

- ボタン認識：G1 の頭カメラで撮った画像を、まず 150〜300 枚用意する。背景を変えたもの（2〜3割）と、ボタンが写っていない画像（1割）も混ぜる。
- 方式は「1クラス検出（button）＋枠内の明るさで点灯を判定」を第一候補にする。精度が足りなければ、2クラス（off / on）検出に切り替える。
- 押した後に点灯したかを確認し、点かなければ少し深く押し直すループを②に組み込む。
