## 5. lowstate の受け取りの CPU
### 予想と違ったこと
- 予想: 1 通ごとの変換（`parse_lowstate`）が重いので、変換を読むときまで遅らせれば軽くなる。
- 実際: PC2 で受け取り方ごとに測ると、変換はほとんど関係なかった。

| 受け取り方（PC2、8 秒） | 処理した数 | CPU（1 コア = 100%） |
|---|---|---|
| コールバックで変換（今までの押す処理） | 1,042 通 / 秒 | 74% |
| コールバックで、届いた物を置くだけ | 1,042 通 / 秒 | 71% |
| コールバックで何もしない | 1,042 通 / 秒 | 72% |
| **最新 1 件だけ持つ DataReader から、50 Hz で取りに行く** | 46 回 / 秒 | **10%** |

- 原因: lowstate は約 1,000 通 / 秒届き、SDK のコールバックは 1 通ごとに Python の関数を呼び、受信データを Python の形に変換する。これが重い。
- 変えたこと: `common/dds.py` に `LatestLowState`（最新 1 件だけ持つ DataReader。読むときに新しい 1 通があれば取り込む）を足し、
  押す処理（`DdsBackend`）と `LowStateReader` で使う。腕の指令は 50 Hz なので、全部受ける必要はない。
  受け取り頻度を数える `check_connection.py` だけは全部数える必要があるので、今までのコールバックのまま。
- 確かめ方:
  - PC2 の実機で、押す処理の受信部を dry-run（送る口を作らない）で開き、50 Hz で読んだ: **CPU 10%**、読んだ値の古さ 最大 0.3 ms、角度・`mode_machine` は今までと同じ。
  - 途切れたときに古い値のまま残る（今までどおり「何秒途切れているか」で止まれる）ことは、偽の DataReader の単体テストと、
    模擬ロボットのテスト（lowstate が途切れたら止まる）で確かめた。全体のテスト 255 件が通った。

## 6. ボタンの YOLO を ONNX で動かす
PC2 の Python 3.12 では torch で GPU を使えず（CUDA のドライバが古い）、ultralytics も入っていない。そこで重みを ONNX にして
onnxruntime（CPU）で動かす。`configs/elevator.yaml` の `yolo.weights` に `.onnx` を書くと切り替わる。書き出しと確認は
`real/export_button_onnx.py`（使い方は [README](../../README.md) の「PC2 で動かす（ONNX）」）。

### 予想と違ったこと
- 予想: Perception で人の検出に使った書き出し方（`nms=False`、end-to-end の出力）をそのまま使えば、`.pt` と同じ結果になる。
- 実際: 45 枚すべてで結果が違った。確からしさが 1.0 に張り付き、4 個のボタンが 2 個になるなど。
- 原因の切り分け:
  1. ONNX を Perception の `onnx_yolo.py` で動かした結果と、同じ ONNX を ultralytics で動かした結果は完全に一致 → 読み方は正しい。
  2. 違うのは `.pt` と書き出した ONNX の間。書き出しの設定を変えて試すと、**出力の形（end2end）だけが原因**だった。
     YOLO26 には「重なりを間引かずに 1 つずつ出す出口」（end-to-end）と「候補を全部出して後で間引く出口」（従来型）の 2 つがあり、
     `.pt` の推論は従来型を使っている。`nms=False` を付けると end-to-end の出口で書き出される。
- 変えたこと: `end2end=False`（従来型）・opset 17（PC2 の TensorRT 8.5 でも読める）で書き出す。

### 結果
| 確かめたこと | 結果 |
|---|---|
| 同じモデルか（`.pt` も 640×640 の正方形に入れて比べる。検証用 30 枚＋ラボのエレベーターの写真 15 枚） | **45 / 45 で一致**（確からしさの差 0.000） |
| 今の使い方との差（ultralytics は `.pt` を横長のまま入れる） | 個数と矢印が同じ 44 / 45、確からしさの差 最大 0.18。残り 1 枚は、確からしさが境目（0.4）近くのボタンが 1 つ ONNX で出なかった |
| 1 枚の時間（候補づくりを含む） | ノート PC: `.pt` 289 ms / `.onnx` 96 ms。**PC2: 4 スレッド 179 ms**（全コア 397 ms）、準備 0.2 秒 |
| PC2 で torch・ultralytics を読み込まないか | 読み込まない |
| 評価環境（realistic、練習用の 20 試行、`.onnx`） | **20 / 20**、点灯までの平均 9.07 秒（`.pt` と同じ）、壁・柱との接触力 最大 2.0 N（1 試行） |

- 書き出したのは今の既定の重み（`_local/button_press/button_yolo/weights/best.pt`）。最終版（`runs/final8`）を既定にしたら、
  `real/export_button_onnx.py --weights <その .pt>` で書き出し直す。

## 7. 人の検出（Perception）の書き出しも直した
6 と同じ書き出し方（`nms=False`）だったので、人の検出の ONNX と、PC2 の TensorRT のエンジンも `.pt` と少しずれていた。
10/22 に作った確認は「同じ ONNX を ultralytics で動かした結果」と比べていたので、このずれに気づかなかった。

| bus.jpg の人の確からしさ | |
|---|---|
| `.pt` | 0.855 / 0.846 / 0.839 / 0.556 |
| 前の ONNX（end-to-end） | 0.92 / 0.90 / 0.86 / 0.52 |
| **直した ONNX（従来型）** | **0.855 / 0.846 / 0.839 / 0.556**（`.pt` と一致） |

- `Perception/real/export_onnx.py` を `end2end=False`・opset 17 にし、確認の相手を `.pt`（正方形に入れる）に変えた。テスト（`test_onnx_detector.py`）も同じ。
- PC2: 前のファイルは `~/perception/old_end2end_20261031/` に移し、新しい ONNX から TensorRT のエンジンを作り直した。
- PC2 で確かめた結果（GPU は TensorRT 8.5・FP16・システムの Python 3.8、CPU は onnxruntime・`lerobot` の Python 3.12）:

  | 画像 | `.pt`（ノート PC） | TensorRT（PC2） | ONNX（PC2） |
  |---|---|---|---|
  | bus.jpg | 0.855 / 0.846 / 0.839 / 0.556 | 0.854 / 0.846 / 0.839 / 0.556 | 0.855 / 0.845 / 0.837 / 0.557 |
  | zidane.jpg | 0.894 / 0.794 | 0.895 / 0.796 | 0.897 / 0.793 |
  | PC2 の Web カメラの写真（640×480） | 0.687 / 0.314 | 0.682 / 0.315 | 0.687 / 0.314 |
  | 1 枚の時間（中央値） | — | 約 20 ms | 約 101〜115 ms |

  - どれも `.pt` との差は 0.005 以下（TensorRT は FP16 なので少しだけ違う）
  - エンジンの作成は約 13 分。`trtexec` の推論だけの時間は 5.4 ms（前の end-to-end のエンジンは 5.6 ms）
  - GPU の 1 枚は前の 17 ms から約 20 ms に増えた。重なりの間引き（NMS）を Python で行う分
- 注意: ultralytics 8.4.164 は `end2end=False` に「将来なくなる書き方」という注意を出す（今は正しく動く）。ultralytics を上げたら書き出しと確認をやり直す。
