# 調べるときに間違えやすいこと（AI が間違えた点）

## 仮定の値から出した結論を、事実のように伝えない

- **日付**: 2026-10-21（10-22 に取り下げ）
- **プロジェクト**: G1 ボタン押し
- **前提バージョン**: —
- **状況**: カメラが 71° 下を向いているという測定から、「エレベーターのボタン（床から 1.03〜1.10 m）は押せる距離では頭カメラに
  写らない」と「大事な見通し」として伝えた。翌日、ユーザーが取り下げた: ボタンの高さは仮定の値で、ラボでは車いす用の低い
  ボタンを押す。71° も首が傾いていたためで、通常は約 45°
- **原因**: 「ボタンの高さ」と「カメラの角度」という、どちらも確かめていない前提を組み合わせて、強い結論を出した
- **対処**: 結論を伝えるときは、使った前提（測ったものか、仮定か）を並べて書く。仮定に頼る結論は「この前提なら」と条件付きにし、
  前提を確かめる方法（メジャーで測る、など）を添える
- **教訓**: 測ったことと、仮定から計算したことを分けて書く

## 前回と値が違うとき、原因を一つに決めつけない

- **日付**: 2026-10-21（10-22 にユーザーが訂正）
- **プロジェクト**: G1 ボタン押し
- **前提バージョン**: —
- **状況**: カメラの角度が 10/14 は 45.9°、10/21 は 71° だった。最初は「カメラが動いた」、ユーザーに聞かれて「10/14 は座っていて
  上体が傾いていた可能性が高い」と推測を記録した。実際は首が傾いていた（10/21 の方がふだんと違った）
- **原因**: 記録に姿勢や IMU が無く判断できないのに、もっともらしい説明を「可能性が高い」として書いた。どちらの日が普通かも確かめなかった
- **対処**: 判断の材料が無いときは「分からない」と書き、次に確かめる方法を書く。比べる値には、そのときの状態（姿勢・IMU）を一緒に残す
- **教訓**: 2 つの日の値が違うとき、「どちらが普通か」から確かめる。測ったときの状態を記録していなければ、原因は推測にとどめる

## 人に貼ってもらう文字列を、省略して書いた

- **日付**: 2026-10-31
- **プロジェクト**: G1 ボタン押し
- **状況**: PC2 の `authorized_keys` に公開鍵を足してもらうとき、`echo 'ssh-ed25519 …' >> ~/.ssh/authorized_keys` と、鍵を `…` で省略した形で書いた。
  ユーザーがそのまま実行して、無効な行が入った。ターミナルの文面を書き写して保存するときも、1 か所写し間違えた（数値 +0.353 を +0.368 と書いた）
- **原因**: 「例」のつもりの書き方が、コピーして実行できる形に見えた。長い文面を手で書き写した
- **対処**: 人が実行するコマンドは、省略せずに、そのまま動く完全な形で出す（鍵なら `cat` した結果を貼る）。貼られた文面を保存するときは、
  保存したあとに、元と見比べる
- **教訓**: 実行される前提の文字列に、プレースホルダを入れない
