# 実機（G1・PC2・カメラ）と開発環境で分かったこと

班で共有するための、短い知識のまとめ。手順は `real/REAL_DAY_PROCEDURE.md`、日ごとの記録は `real/DAILY_LOG_*.md`、
シミュレーションでの結果は `README.md` の「エレベーターの呼びボタン」を参照。

## G1・PC2

- **無線では lowstate も腕の指令も届かない。** G1 の DDS は中の有線（192.168.123.x）だけを流れる。無線（PC2 の
  192.168.0.82、DHCP）でできるのはカメラ（配信・受信・YOLO・収録）だけ。腕と lowstate は有線のラボ PC で（2026-09-29、10-14）
- **`run_g1_server.py` は起動時に `MotionSwitcherClient.ReleaseMode()` を実行し、歩行の制御を解除する。** 立っているときに
  起動すると倒れるおそれがある（`Perception/real/README.md`）。lowstate を無線に中継する目的では使わない
- PC2 では Unitree の `videohub_pc4 /dev/video4`（頭のカラー）と **`videohub_pc4_chest /dev/video10`（胸のカメラ）** が
  root で常駐している（2026-10-14）。止めない
- PC2 の `lsusb` は D435i（`8086:0b3a`）を「Intel Corp. 4-Port USB 3.0 Hub」と表示する。名前ではなく ID で探す

## 頭のカメラ（RGB-D）

- **頭カメラの向きは、首の傾きで変わる。** 通常は水平から約 45° 下（2026-10-14、深度から 45.9°。URDF は 47.6°）。
  2026-10-21 は首が傾いていて 71° だった（床と机の面・FK の指先の投影で確認）。**毎回、最初に向きを確かめる**
  （立った状態で IMU も記録しながら、深度から床と机の面の pitch を求める）。首が傾いたままのときだけ、
  `configs/camera.yaml` の `head_camera_mount`・`depth_anchor` のコメントを外す（既定は上書きしない）。71° のときは
  天板の高さで見えるのは pelvis から前 約 40 cm まで（`real/DAILY_LOG_20261021_labpc.md`）
- 実機に**胸のカメラは見当たらない**（10/14 に `videohub_pc4_chest /dev/video10` のサービスは動いていたが、10/21 の再起動後は
  無かった。窓口だけだった可能性が高い。未確認）。カメラは頭の D435i だけと考える
- **videohub のカラーが古い画像のまま止まることがある**（2026-10-21）。深度は動くので、位置合わせがずれて YOLO も外れる。
  配信サーバの起動し直し・USB の差し直しでは直らず、G1 の再起動で直った。配信を始めたら、カラーが動いているかを最初に見る
- videohub がカラーを使っていても、**深度だけなら RealSense から開ける**（USB のインタフェースが分かれている）。
  `rgbd_server.py --source videohub` は、カラーを videohub から受け取り、深度を自前でカラーに位置合わせする
- 2026-10-14 に実機で確かめた: 5 fps（`--max-fps 5`、無線）、カラー 640×360、内部パラメータ fx 454.2・fy 453.8・
  cx 318.6・cy 190.7、深度 → カラーの平行移動 [0.015, -0.0004, 0.0003] m。向き・色・輪郭の重なりは正しい。
  カラーと深度の撮った時刻の差 約 30 ms、位置合わせの計算 約 100 ms（PC2）、受信までの遅れ 約 170 ms
- 深度の画像に、値 0 の点が規則的に並ぶ（約 2.7%。640×480 → 640×360 に並べ直すときのすき間）。ボトル・ボタンは
  領域の中央値で深度を取るので影響しない
- `configs/localize.yaml` の深度の上限は 1.5 m。床に置いたボトル（1.59 m）は YOLO が見つけても位置が出ない
  （「有効な深度が 0 画素」）。腕が届く範囲（0.5 m 前後）で試す。机の上 0.60 m では確信度 0.83、5 枚のばらつき 3 mm 以内

## ラボのエレベーターの呼びボタン（2026-10-15、スマホの写真 5 枚。G1 のカメラではない）

- 黒い柱に、一般用の ↑↓ と、その下に車いす用の ↑↓ がある。**点灯すると、ボタンの縁の細い輪（青みがかった白）
  だけが光る**。面と矢印は変わらない。枠全体の明るさの平均では輪の光が薄まるので、点灯の確認は明るい部分で見る
  （README の「確かめる」）
- **YOLO** は 5 枚とも 4 つのボタンをすべて見つけた。向きは、消えているボタンでは正しく、点灯した ▼ を 3 枚中 2 枚で
  「up」と読み違えた（点灯したボタンを学習していない）。点灯の確認では枠の位置だけを使うので影響しない
- **classic** は、本物の線の矢印（↑↓）の向きを全部逆に読む（シミュレーションのボタンは塗りつぶした ▲▼）。▲▼ の組は
  上下の位置で決めるが、読んだ向きが並びと合わないと組として認めないので、見つけられない。**このエレベーターでは
  YOLO を使う**（`J1GEN_BUTTON_DETECTOR=yolo`）

## 開発環境

- **YOLO を使う評価をノート PC（WSL2）で並列に回すときは `--workers 4`。** 1 プロセス約 2.5 GB（YOLO なしは約 1.7 GB）。
  11 並列で WSL2 ごと落ちた（2026-10-12）
- **GPU が複数ある PC では、nvidia-smi と PyTorch で GPU の番号が逆になることがある。**
  `CUDA_DEVICE_ORDER=PCI_BUS_ID CUDA_VISIBLE_DEVICES=<nvidia-smi の番号> ... --device 0` で選ぶ。RTX 50 系は `cu128` の torch
- **main への PR の流れ（2026-10-28、PR #57）**: main は「各自でレビューする」方針で、CI が唯一の機械的な確認。CI は変えたフォルダ
  （と依存するフォルダ。Button_Press は Perception に依存）のテストだけを実行する。出す前に main を `git merge origin/main` で取り込み、
  `CI_CHANGED_FILES="$(git diff --name-only origin/main...HEAD)" PYTHON=G1_HuggingFace/venv/bin/python bash scripts/ci/run_all_tests.sh` と
  `scripts/ci/run_checks.sh`（構文・変えた Markdown のリンク）を手元で通す。`rebase` は共有している履歴を書き換えるので使わない。
  競合は `git merge-tree --write-tree --name-only origin/main HEAD` で先に試算できる。マージは PR を作った本人が画面で押す
- この PC のシステムの Python は `pip install` が PEP 668 で止まるので、`Perception/tests/run_tests.sh` は NG になる（コードの問題ではない）。
  venv の Python で `PYTHONPATH=Perception python -m unittest discover -s Perception/tests` を直接回す。`gh` は別の端末で `sudo apt install gh` と `gh auth login`
- YOLO の最初の 1 回の推論は遅い（ノート PC の CPU で 1.1 秒、2 回目から約 0.17 秒）。実時間で動く模擬 G1・実機では
  その間ロボットが待つので、`YoloButtonDetector` は読み込み時に 1 回推論しておく

## シミュレーションの評価の読み方

- 評価環境は**ボタンが点灯した瞬間に試行を終える**ので、点灯したあとの動き（押し続ける・確かめる・腕を戻す）の問題は
  数字に出ない。点灯で終わらせない診断で確かめる（2026-10-14: 点灯後の押し込みで柱に 7〜22 N かかる配置があった。
  2026-10-15 に直した。次の項目）
- **かたい止まりに当たったら、目標を奥に置いたまま押し続けない。** 腕は弱い PD なので、押す力は「指令と実際の
  指先の差（遅れ）」で決まる。ボタンが底に着いたあとも面の 15 mm 奥を目標にすると、遅れが 26 mm まで増え、
  中心からずれた位置を押していた指先が横に滑って柱の穴の縁を 21.6 N で押した。遅れが 5 mm を超えたら止めて、
  実際の指先の 2 mm 先を押したまま保持する（最大 5.0 N に）。触れる前の遅れは評価環境で最大 1.9 mm
- 評価の接触力は「ロボットと壁・盤」だけで、**ロボット自身の体どうしの接触は入らない**。押す向きと逆にまっすぐ下がると、
  柱が近い（31 cm）とき 10 cm 以上で右の手首が胴体に入った。腕は来た経路を逆にたどって戻す
- realistic のカメラの取り付けのずれ（角度 最大約 ±1.5°）で、ボタンの位置の推定が押す向きに最大 19 mm ずれる。
  実機でも同じことが起きるので、段階4の較正（`configs/localize.yaml` の `offset_pelvis_m`。ボタンにも使われる）が大事
- **シミュレーションは腰（pelvis）を固定している**（J1-gen も Yada さんの評価環境も）。実機は足側のバランス制御が
  腰を動かすので、腕を伸ばしたときや押した反動で、測った対象の位置と腰の関係がずれる。どれだけずれるかは実機で測る:
  ボトルは全体をつなぐスクリプトが終わったときに表示する（`body_motion.csv`）、エレベーターは `J1GEN_BODY_LOG` を付けて
  動かし `real/body_motion.py` で読む（README の「押している間の体（pelvis）の動き」）。脚の関節角の FK で求めるので、
  新しいトピックは要らない

## 車いす用の ▲▼ の立つ位置の地図（計画だけ、2026-10-29）

- `sim/elevator_stand_map.py`: ラボの車いす用の組（pelvis から ▲ z +0.21・▼ z +0.14、間隔 7 cm）を、柱の面までの距離 x・ボタンの左右 y・柱の面の傾き（±10°）で振り、
  実際の計画（`ElevatorPressController._plan`）が通るかと、頭カメラ（約 48° 下向き）にボタン 2 つと柱の面の範囲が入るかを調べる。開始は 10/21 の実機の立った姿勢。1,540 通り、40 秒
- **今の勧める範囲（柱まで 29〜40 cm、左右 6 cm 以内）の中は、ほぼ全部通る**（傾き ±10° も含めて 178/180。落ちた 2 つは傾き ±10° の端: 関節の速さの上限 0.0108 > 0.0100 の
  ぎりぎりと、肘が胴体に当たる）。範囲は妥当
- 通る範囲はもっと広い（傾き 0°、▲▼ とも）: 距離 26〜44 cm、左右は右 12 cm〜左 12 cm（距離によって狭くなる）。傾き ±5° 以内なら、距離 28〜40 cm × 左右 −8〜+4 cm の長方形が全部通る。
  外れる理由: 近い（24 cm 未満）と柱・壁に当たる、左 16 cm 以上は右腕の作業空間の外（W）、遠い（44 cm 以上）は関節の速さの上限（J）、右へ寄る（−16 cm 以上）と画像から外れる
- **不具合を見つけて直した**: 実機の立った姿勢では、下ろした手が股関節の当たり判定に入っている（−7 mm）。エレベーターの `_check_wall` が、これを「柱・壁に当たる」と断り、
  **どの位置でも計画が立たなかった**（評価環境の開始姿勢には股関節の接触がないので気づかなかった）。最初の区間は開始より近づかない間は許すようにした
  （`PressPlanner.plan` と同じ）。評価環境（classic、練習用の 20 試行）は 20/20・平均 8.5 秒のまま

## ボトルを押せる机の位置の範囲（計画だけの地図、2026-10-29）

- `sim/reach_map.py`: 机の縁 x・縁からボトルまで・左右 y・天板の高さ・縁の傾きを振って、実際の計画（IK・体と机との衝突・経由の姿勢を通る動き）が通るかと、
  頭カメラ（約 48° 下向き）の画像にボトルが全部入るかを調べる。開始の姿勢は 10/21 の実機の lowstate。8 秒で 1,456 通り
- **今の `via_pose` では、机の縁が 32 cm 以上、ボトルが体の右 10〜30 cm のときだけ通る**（249/1456）。10/21 の「縁 31〜32 cm、ボトルは縁ぎりぎり」と合う。
  断る主因は、開始→経由の途中で手首が机に当たること（544 件）と、手前の姿勢で腕が胴体に 1 cm 未満に近づくこと（ボトルが右 10 cm より内側、421 件）
- `sim/via_search.py`（ランダムに 300 通り）→ `sim/via_refine.py`（山登り）: 経由の姿勢 `[68.3, -11.1, -40.9, -43.9, 0, -4.1, 0]` [deg] で
  **684/1456（2.7 倍）、机の縁が 18 cm 以上でも通る**。学習に使っていない格子でも 122 → 418（3.4 倍）。開始の腕を ±4° ずらしても 2.5〜2.8 倍、
  余裕（clearance）を 0.005〜0.015 に変えても同じ。ただし **MuJoCo・実機では未確認**（`pipeline.yaml` の `via_pose` には、まだ入れていない）
- **指の向きを左へ傾ける**（`sim/approach_search.py`、`pipeline.yaml` の `finger_tilts_deg`。手先は押す向きにまっすぐ、指だけ傾く）と、
  ボトルが体の右 10 cm より内側でも通る（右 10 cm〜左 5 cm の配置で 0 → 9〜11 / 12）。新しい経由の姿勢と合わせると **1140/1456（今の 249 の 4.6 倍、
  画像にも入る 808）**。今の経由のままで指の向きだけだと 390、経由だけだと 684。開始の腕を ±4° ずらしても 1032〜1087、余裕を変えても 1138〜1145。
  下向き（上 −15°）を足すと通る数は増える（1089 → 1127）が、**MuJoCo ではハンド（衝突の箱）の側面がボトルに先に触れ、指先が面の手前 12〜35 mm で止まる**
  （左 45°・下 15° で 29 mm、60° で 15 mm 進むだけ）ので、左へ傾けるだけの候補 `[[0, 0], [15, 0], [30, 0], [45, 0]]`（小さい順に試す）にした。
