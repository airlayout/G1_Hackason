# 失敗ログ

このフォルダでの開発中に実際に起きた失敗と、その原因・反省・再発防止策を記録する。
新しい失敗が起きたら、下のテンプレートに沿って追記する。

## テンプレート

```
## YYYY-MM-DD: 失敗の一言タイトル

**何が起きたか**
（観測された事実。憶測ではなく実際に見えたことを書く）

**原因**
（コード上・手順上の根本原因）

**反省**
（なぜ事前に気づけなかったか。見落としていた前提は何か）

**再発防止策**
（実際にコード/手順をどう変えたか）
```

## 2026-08-26: 計測中にEthernetが抜け、停止処理が失敗して地図が保存されなかった

**何が起きたか**

実機での初回試験で、Mapping中にEthernetケーブルのリンクが落ちた（`carrier=0`）。
`./mapctl stop`が次のように失敗した。

```
[FAIL] map.pcd: map_raw.pcdがありません
[FAIL] raw.rosbag2: rosbag2 metadataがありません
[PASS] trajectory: 3070 poses
[WARN] backend停止: g1_onboard: enp3s0: does not match an available interface.
[WARN] PCD回収: ssh: connect to host 192.168.123.164 port 22: Connection timed out
```

同じことが2セッション連続で起きた。G1を全探索した結果`/home/unitree/maps/`自体が
存在せず、**PCDは1つも生成されていなかった**。

**原因**

停止時に通信が無いと、G1へ`kEndMapping`(1802)が届かない。PCDの書き出しはこのコマンドが
引き金なので、G1は地図を保存する機会がないまま待機状態へ戻る。回収以前に、回収すべき
ファイルが存在しない。

rosbag側は別の原因で、recorderコンテナが停止処理を完了できず`metadata.yaml`が
書かれないまま残っていた。`db3`自体は1.56GBが正常に書き込まれていた。

**反省**

「rosbagへ並行記録してあるから現場で地図ができなくても持ち帰れる」という設計になって
いたにもかかわらず、**その持ち帰ったデータから地図を作る手段を用意していなかった**。
保険をかけたつもりで、保険金の受け取り方を決めていなかった。

またケーブルの取り回しを軽視していた。歩行させる以上ケーブルは動くのに、抜けることを
リスクとして手順に書いていなかった。実際には2回続けて抜けている。

**再発防止策**

1. `mapctl rebuild`を追加した。rosbagの地図点群を蓄積して`map_raw.pcd`を作り直す。
   `db3`を直接読むので`metadata.yaml`が無くても動き、ROS 2もDockerも要らない。
   実測では3,108メッセージ/310万点から324,112点の地図を2.3秒で再構成し、
   `mapctl validate`が全項目PASSした（有限値率1.000、範囲43.0m×38.6m×3.8m）。
2. コンテナは**強制終了せずSIGTERMで正常終了させる**と、rosbag2が自分で
   `metadata.yaml`を書き出すことを確認した。`docker stop -t 30 <container>`で足りる。
   復旧手順として`FIELD_RUNBOOK.md`第6節に明記した。
3. `FIELD_RUNBOOK.md`第1節に、ケーブルの取り回しを固定する項目を追加した。

→ 教訓として一般化すると: **「壊れても後で復旧できる」という設計は、復旧する手順を
実際に動かして確かめるまで完成していない。** 記録を残す仕組みと、記録から成果物を
作る仕組みは、対で用意する。

## 2026-08-26: 現場PCのstatic IPが既に使われていて接続できなかった

**何が起きたか**

`Common/network/setup_ethernet_for_g1.sh`が設定する`192.168.123.200/24`で、
NetworkManagerの接続が有効化できなかった。

```
エラー: 接続のアクティベーションに失敗: IP 設定を確保できませんでした
```

`.222`へ変更したところ成功した。後からリンク上を調べると、G1本体(`.164`)以外にも
`.120` `.161` `.200`が応答しており、**`.200`は別の機器が使用中**だった。

**原因**

G1のEthernetリンクにはG1本体だけでなく複数の機器がぶら下がっている。スクリプトが
既定値として持っていた`.200`が、そのうちの1台と衝突した。

**反省**

「G1は`.164`固定だから、それ以外なら空いている」と暗黙に仮定していた。実際には
リンク上に何台いるかを確認していなかった。切りのよいアドレスほど他機器も使いやすい。

**再発防止策**

`FIELD_RUNBOOK.md`第2節に、空きアドレスの確認方法(`ip neigh show`、`ping`)を追記した。
`setup_ethernet_for_g1.sh`の既定値は`.200`のままなので、**別環境で使う際は衝突を
前提に確認すること**。

## 2026-08-26: mapctl view --live がRVizを起動できなかった

**何が起きたか**

```
malformed launch argument 'pcd_path:=', expected format '<name>:=<value>'
```

**原因**

ライブ表示ではPCDを読まないので`pcd_path`が空文字になるが、`compose.py`が無条件に
`pcd_path:={値}`を渡していた。`ros2 launch`は空値をmalformedとして拒否する。

**反省**

保存PCDの表示(`view <session_id>`)でしか試していなかった。`--live`は実機で計測中で
ないと通らない経路なので、実機接続まで発覚しなかった。

**再発防止策**

空のときは引数自体を渡さないよう修正した。`view.launch.py`は
`DeclareLaunchArgument("pcd_path", default_value="")`を宣言済みなので、省略すれば
同じ既定値になる。
