# 失敗ログ

このフォルダでの開発中に実際に起きた失敗と、その原因・反省・再発防止策を記録する。
新しい失敗が起きたら、下のテンプレートに沿って追記する。

## テンプレート

```
## YYYY-MM-DD: 失敗の一言タイトル

**何が起きたか**
（観測された事実。憶測ではなく実際に見えたことを書く）

**原因**
（コード上・手順上の根本原因）

**反省**
（なぜ事前に気づけなかったか。見落としていた前提は何か）

**再発防止策**
（実際にコード/手順をどう変えたか）
```

## 2026-08-25: LiDAR を頭と同じ高さに付けて、点が 1 つも返らなかった

**何が起きたか**
`torso_link` に取り付けた LiDAR で `mj_multiRay` を撃ったところ、11,520 本の
レイのうち有効な点が 0 になった。取り付け位置を少し変えた別の設定では、
点は返るものの後方 360 度ぶんが丸ごと欠落し、`x` の最小値が -0.86（部屋の壁は
-4.95 のはず）で頭打ちになった。

**原因**
取り付け位置を、同じ `torso_link` に定義済みの `head_camera`（ボディ座標 z=0.45、
ワールド z≈1.27m）に合わせていた。しかし `torso_link` の頭部 geom はワールド
z≈1.12〜1.33m を占めており、**LiDAR が頭部メッシュの内側に入っていた**。
全レイが自分の頭に当たり、自己反射として捨てられていた。

**反省**
「カメラが付いている位置なら、そこは外から見える位置のはずだ」と考えたのが
間違いだった。カメラは面に貼り付いていれば機能するが、LiDAR は**その点を中心に
全方位へレイを飛ばす**ため、周囲に自分の体があってはいけない。
センサーの種類によって「取り付け位置に求められる条件」が違うことを見落としていた。

**再発防止策**
既定の取り付け位置を頭の上（ボディ座標 z=0.55、ワールド z≈1.40m）に変更した。
併せて、地図が意図通り取れているかを毎回「点の総数」と「ワールド座標の x/y/z の
範囲」で確認するようにした。範囲を部屋の実寸と突き合わせれば、
今回のような「向きが偏った欠落」もすぐ気づける。

## 2026-08-25: 別スレッドからレイキャストしてプロセスごと segfault した

**何が起きたか**
歩行させながら `mj_multiRay` でスキャンを撮る本番実行が、毎回 tour 開始直後に
落ちた。`Segmentation fault` でプロセスごと死に、標準出力も途中で切れる。
落ちる直前に MuJoCo から次のエラーが出ていた:

```
ERROR mj_copyDataVisual (engine_io.c:1165): attempting to copy mjData while stack is in use
```

**原因**
`mj_multiRay` は一時領域を **mjData のスタックから確保する**。その mjData は
シミュレーション本体の物理演算スレッドが回しており、さらに MuJoCo ビューアの
スレッドが毎フレーム `mj_copyDataVisual` で複製している。
そこへ別スレッド（こちらの収録ループ）からレイキャストを撃ったため、
スタックの取り合いになってメモリ破壊が起きた。

**反省**
`mj_data` を「読むだけ」だと思い込んでいた。実際コードには
「物理演算スレッドと並行して読むが 1 ステップ 1.6mm なので無視できる」という
コメントまで書いていた。**問題は読み取り値の鮮度ではなく、`mj_multiRay` が
mjData に書き込む（スタックを確保する）ことだった。**
「読み取り専用に見える API が、内部で引数のバッファを一時領域に使っていないか」
を確認しないまま、精度の話にすり替えて安全性の検討を終わらせてしまった。

**再発防止策**
`MujocoLidar` がレイキャスト専用の `MjData` を自前で 1 つ持つようにした。
スキャンのたびにレイキャストが参照する `geom_xpos` / `geom_xmat` だけを
ライブの mjData から写し、レイキャスト自体は自前の mjData 上で行う。
これで誰ともスタックを共有しない。
（写している最中に物理演算が 1〜2 ステップ進む可能性は残るが、これは本当に
mm オーダーの話なので、地図の解像度 5cm から見て問題にならない）

## 2026-08-25: 巡回経路上に障害物を置き、G1 がぶつかって動かなくなった

**何が起きたか**
収録は最後まで完走したが、真値の軌跡を見ると G1 は開始 20 秒で (2.9, 1.8) に
到達したあと**そこから一切前進せず**、その場で向きだけ変え続けていた。
歩いた範囲は x [0.00, 3.01] / y [-0.00, 1.91] しかなく、部屋の半分も回れていない。

**原因**
検証用シーンの `box_crate` を (3.4, 2.6) に置いており、その geom は
x 2.8〜4.0 / y 2.0〜3.2 を占めていた。G1 はこの箱の角に突っ込み、
以後ずっと押し当てたまま足踏みしていた。歩行ポリシー
（GrootLocomotionController）には**障害物回避が一切入っていない**。

**反省**
障害物を「ICP の拘束を増やす幾何」としてだけ見ており、
**同じ空間をロボットが歩く**ことを設計に入れていなかった。
また、スクリプトが正常終了して 501 フレーム・540 万点が保存されたため、
ログの `[result]` だけ見ると成功に見えた。実際に気づけたのは
真値の軌跡を時系列で出力してからで、**「完走した」と「意図通り動いた」は
別物**だという当たり前のことを一度見落とした。

**再発防止策**
1. 障害物を全て壁際（|x| >= 3.6 または |y| >= 2.9）に寄せ、部屋の中央を空けた。
2. 収録の最後に「実際に歩いた範囲(真値)」を必ず表示するようにした。
   意図した巡回範囲と突き合わせれば、途中で止まっていればすぐ分かる。
3. 巡回の秒数を実測値ベースで決め直した。`remote.ly=0.5` で前進 約 0.29 m/s、
   `remote.rx=-0.5` で左旋回 約 6.6 deg/s（90 度回るのに 14 秒）と分かったので、
   これを `record_scans.py` のコメントに残した。

## 2026-08-25: 落ちたプロセスの残骸が次の実行を壊した（失敗ではないが要注意）

**何が起きたか**
上記の segfault で落ちたあと、次の実行が「`zmq.error.ZMQError: Address already in
use (addr='tcp://*:5555')`」を出し、さらに
`[UnitreeG1] Waiting for robot state...` のまま接続できなくなった。

**原因**
MuJoCo 環境はカメラ配信用に別プロセス（`multiprocessing` の spawn）を立てる。
親が segfault で死ぬとこの子プロセスが孤児として残り、ポート 5555 を掴んだままになる。
さらに孤児が DDS（ループバック）に lowstate を流し続けるため、
次に起動したシミュレーションと**2 つのシミュレータが同じ DDS ドメインで
混信する**状態になっていた。

**再発防止策（手順）**
実行が異常終了したら、次を実行する前に残骸を確認して落とすこと:

```bash
ss -tlnp | grep 5555          # 掴んでいるプロセスがあれば孤児
pgrep -fa record_scans
```

なお `G1_HuggingFace/README.md` にある通り、MuJoCo 環境は起動そのものが
非決定的に失敗することがある（`SimpleWalk/sim/release_band_and_walk_forward.py`
も同じ条件で 1 回目は `mj_makeConstraint: nefc under-allocation` で segfault し、
2 回目は正常に完走した）。**1 回落ちただけでコードを疑う前に、
残骸を掃除してもう一度実行してみること。**
