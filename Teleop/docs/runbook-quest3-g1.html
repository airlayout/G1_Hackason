UNITREE G1 × META QUEST 3

G1 テレオペ起動手順

電源を入れた状態から、Quest 3 のコントローラで G1 の両腕を動かせるようになるまで。実際に流したコマンドと、そのとき返ってきた値をそのまま載せています。エンジニアでなくても順に追えるように、各手順に「これは何をしているか」を付けました。

実施日 2026-10-01 機体 G1 29自由度 設置 吊り下げ（足は接地） 所要 約25分

最初に読んでください

これは実機の腕を動かす手順です。腕は人を傷つけられる速度と力を持っています。次の4つは省略できません。

  • G1 を吊り下げまたは座位で支持する。立たせたまま行わない
  • 腕の可動範囲に人と物を置かない
  • 電源をすぐ切れる位置に人を配置する
  • 初めてのときは2人以上で行う

全体の流れ

やることは大きく4つです。つなぐ → 確かめる → ロボットの制御権を空ける → テレオペを起動する。このうち3番目が一番つまずきます。

  1. 1有線 LAN でつなぐハブ経由でも可。無線では行わない
  2. 2疎通と機体構成を確かめるロボットは動かない
  3. 3腕を動かせる状態か確かめるロボットは動かない
  4. 4arm_sdk が使えるか試す左肩が約3°だけ動く
  5. 5ai を解除してデバッグ状態にするバランス制御が止まる
  6. 6リモコンでダンピングに入れる人の手でしかできない。最大の関門
  7. 7テレオペを起動する両腕がゼロ姿勢へ動く
  8. 8Quest 3 をつなぐブラウザで開いて VR に入る
  9. 9追従を開始するここから腕が手に付いてくる

PC で実行人の手で行う

Python（専用環境）/home/ubuntu/miniforge3/envs/tv/bin/python

作業フォルダへ移動
cd /home/ubuntu/g1-starter-kit
01

有線 LAN をつなぐ

ロボットは動きません

一言で：ロボットと PC を LAN ケーブルでつなぎ、電気的につながったことを確かめます。

腕の制御は 1秒間に250回のやり取りをします。無線だと遅れのばらつきで動きが乱れ、しかも「止めろ」という指令も同じ道を通るため、切れたときに止められません。だから有線でしか行いません。ハブを挟んでも問題ありません。

リンクの確認
ip -br addr show enp129s0
ethtool enp129s0 | grep -E "Link detected|Speed"

成功のしるし

enp129s0  UP  192.168.123.200/24
    Speed: 1000Mb/s
    Link detected: yes

ハブを使うときの注意

Link detected: yes が出ても、それはハブとつながっただけかもしれません。ロボットまで届いているかは次の手順の ping で判断します。実際にこの日は、ロボットの電源が入るまで carrier=0（信号なし）のままでした。

02

疎通と機体構成を確かめる

ロボットは動きません

一言で：ロボットに声が届くか、そして「腕が何本の軸でできた機体か」を自動で判定します。

G1 には腕の軸数が23本のものと29本のものがあり、間違えると腕の動きの計算が合いません。手首の軸数で決まるので、人が目で数えるより機体に聞いたほうが確実です。

疎通・構成の確認
./scripts/preflight.sh

成功のしるし（この日の実測）

[OK] リンク UP・静的IP あり
192.168.123.161  ping応答  制御演算ユニット
192.168.123.164  ping応答  開発演算ユニット PC2
[OK] 受信 3120 件 / 1040 Hz
     左腕 7軸 / 右腕 7軸 / 腰 3軸
[OK] 機体構成の判定: --arm=G1_29

1040 Hz は、ロボットが自分の状態を1秒に1040回報告しているという意味です。この数字が出れば通信は健全です。

03

腕を動かせる状態か確かめる

ロボットは動きません

一言で：「腕のモーターに電気が入っているか」と「指令を送る道が空いているか」の2点を見ます。

ここが手順全体でいちばん大事です。この2つが揃っていないと、指令を送っても腕は1ミリも動かないのに、画面には「送信成功」と出ます。原因が分からず延々と悩むのは、ほぼこれです。

状態の確認
/home/ubuntu/miniforge3/envs/tv/bin/python tools/mode_check.py --iface enp129s0

この日の実測

1. モーションコントローラ
   'ai' が稼働中 → 規格上の経路: rt/arm_sdk
2. 腕のモータ
   有効（mode=1）
見るところ必要な状態この日
腕のモーターmode=1（電気が入っている）OK
指令を送る道空いているふさがっていた

道がふさがっていたのは、ロボット自身の歩行制御プログラム（ai）が同じ道を1秒に1000回使い続けていたからです。ここにテレオペが1秒250回で割り込んでも、1000回のほうに上書きされて消えます。だから次の手順で道を空けます。

04

もう1本の道が使えるか試す

左肩が約3°動きます

一言で：「ai を止めずに腕だけ借りる」近道が、この機体で通用するかを最小の動きで試します。

規格上は rt/arm_sdk という別の道があり、歩行制御を止めずに腕だけ操作できるはずです。使えるなら手順5・6を飛ばせます。ただし機体によって応じないことがあるので、左肩を0.05ラジアン（約3°）だけ動かして実際に確かめます。

arm_sdk が効くかの試験
/home/ubuntu/miniforge3/envs/tv/bin/python tools/armsdk_probe.py --iface enp129s0 --yes

この日の結果：効かなかった

対象: L_ShoulderPitch  現在 -0.1090 rad → 目標 -0.0590 rad
  ① 制御権 0→1   weight=1.00  実測=-0.1090  偏差=+0.0000
  ② 目標へ        weight=1.00  実測=-0.1090  偏差=+0.0000

指令した変位 : +0.0500 rad  /  実測の最大変位: +0.0000 rad
❌ arm_sdk が効いていません。

「腕を貸してください」と正しく頼み、ロボットも受け取ったように見えるのに、実際には1ミリも動きませんでした（実測変位 0.0000）。この機体はこの近道に応じません。よって残る道は1つだけで、手順5へ進みます。

この試験を省かないこと

省くと、あとで「腕が動かない」ときに原因が機体なのか設定なのか分からなくなります。3°の動きで切り分けられるので、毎回やる価値があります。

05

ai を解除してデバッグ状態にする

バランス制御が止まります

一言で：ロボット自身の歩行制御を止めて、指令の道をテレオペに譲ります。

実行前に必須

これを行うとバランス制御が止まります。吊り下げか座位で支持されていることを必ず確認してください。また実行直後にモーターの電気が切れて脱力します。リモコンを手元に用意し、機体に手を添えられる位置にいてください。

ai の解除
/home/ubuntu/miniforge3/envs/tv/bin/python tools/mode_check.py --iface enp129s0 --release

成功のしるし

'ai' を解除します ...
解除しました。デバッグ状態です（rt/lowcmd が効きます）。

1回目は失敗しました

この日の1回目は、6回試してすべて status=3104（送ったが返事が来ない）で失敗し、「リモコン側で操作してください」と出ました。もう一度同じコマンドを流したら成功しました。 散発的に失敗する通信なので、失敗しても1〜2回やり直してください。失敗しても何も起きません。

解除後の状態を見ると、狙いどおり道は空きましたが、モーターは全部切れていました。

解除直後の実測

rt/lowcmd = 0.0 Hz        ← 道が空いた（狙いどおり）
腕mode=[0] 脚=[0]         ← 全モーターが脱力（想定内）
06

リモコンでダンピングに入れる

人の手でしかできません

一言で：脱力したモーターに、リモコンの操作で電気を入れ直します。

これはソフトからは絶対にできません。 ロボット側の安全設計で、リモコン操作でしか電気を入れられないようになっています。指令に「電気を入れて」と書いても無視されます。

やり方結果
リモコンでダンピング（FSM 1）に入れるこれだけが有効
指令に mode=1 と書いて送る効かない
プログラムから Damp() を呼ぶ解除中は応答しない

ここが最大の関門 ── 時間との勝負です

ダンピングに入れても、指令が届かない状態が続くと数十秒でまた脱力します。この日は実際に、ダンピングを確認してから手作業でテレオペを起動するまでの約30秒の間に脱力し、起動が弾かれました。

そこでダンピングを検知した瞬間に自動でテレオペを起動するやり方に変えました。これで待ち時間がゼロになり、一度で成功しました。

監視スクリプトを動かしておき、その状態でリモコンを操作します。検知すると自動で手順7が始まります。

監視を開始して待つ（この状態でリモコンを操作）
setsid nohup /home/ubuntu/miniforge3/envs/tv/bin/python -u \
  watch_and_launch.py teleop.log > watch.log 2>&1 < /dev/null &

この日の実測

STATE  t=   0.0s  arm_mode=[0]  lowcmd=free
STATE  t=  71.7s  arm_mode=[1]  lowcmd=free   ← 入った

リモコンの操作から0.05秒以内にテレオペが起動しました。

07

テレオペを起動する

両腕がゼロ姿勢へ動きます

一言で：Quest とロボットをつなぐ本体プログラムを立ち上げます。

手順6の自動起動を使わず、人が直接起動する場合はこちらです。普通はこの形で使います。

通常の起動（ターミナルでキー操作する）

この形では、立ち上がったターミナルで r（追従開始）、q（終了）を押して操作します。終了は必ず q。 Ctrl+C だと腕が戻らないまま止まります。

この日は自動化のために、キーの代わりにプログラムから指示を送れる形で起動しました。

この日実際に使った起動（プログラムから操作する形）
./scripts/teleop.sh --ipc --headless

成功のしるし ── 2つの関門を通過

[OK]  デバッグ状態 → rt/lowcmd を使います
[OK]  腕モータ有効（mode=1）

  機体         : G1_29
  指令トピック : rt/lowcmd

  https://192.168.0.167:8012/?ws=wss://192.168.0.167:8012

この2つの [OK] が出れば、手順3〜6が正しく効いたという証明です。どちらかが欠けていると、ここで止まって理由を教えてくれます。

08

Quest 3 をつなぐ

ヘッドセットの操作

一言で：Quest のブラウザで PC の画面を開き、VR モードに入ります。

Quest 側にアプリを入れる必要はありません。ブラウザだけで動きます（開発者モードも不要です）。Quest と PC が同じ無線ネットワークにいることが条件です。

  1. Quest を PC と同じ WiFi につなぐ
  2. Meta Quest ブラウザで手順7に表示された URL を開く
  3. 証明書の警告が出たら「詳細設定」→「アクセスする」（自己署名証明書なので正常です）
  4. G1 の方を向いて Meta ボタン長押し →「ビューをリセット」
  5. ページの「Virtual Reality」ボタンを押し、権限をすべて許可する
  6. G1 を直接目で見られる位置に立つ。ヘッドセットには周囲の現実（パススルー）が映るだけで、G1 のカメラ映像は映りません

ページを開くだけでは足りません

「Virtual Reality」ボタンを押して没入ビューに入るまで、頭と手の位置は送られません。ここを飛ばすと「つながっているのに腕が動かない」になります。

ヘッドセットに G1 のカメラ映像は映りません

「Virtual Reality」ボタンを押しても、見えるのはパススルー（自分の周囲の現実）だけです。ロボット視点の映像は出ません。

理由は、カメラ映像を送るにはロボット内蔵のもう1台のコンピュータ（PC2）で画像サービスを別に起動する必要があるからです。この手順では起動していません。実際、テレオペ起動時のログにこう出ています。

WARNING Request to 192.168.123.164:60000 timed out or no response, using local config.

この日の teleop 起動ログ。192.168.123.164 が PC2 で、画像サービスが応答していないという意味です。

公式ドキュメントでも、映像を見るには実機では画像サービスを手動で起動すること、そして https://192.168.123.164:60001 を開いてカメラのプレビューを確認できることが案内されています。

“the robot’s first-person view in the headset” ... in physical deployment: must be manually started on PC2

出典: unitreerobotics/xr_teleoperate README

そのため、この構成では G1 を自分の目で直接見ながら操作します。G1 が見える位置に立ってください。手順4の「G1 の方を向いてビューをリセット」が大事なのもこのためです。

映像が無くても腕は動きます ── 頭とコントローラの相対位置で決まります

映像が映らないので「まだ何も起きていない」と感じますが、姿勢データはすでに送られています。この直後の手順09で追従を開始すると、すぐに腕が動き始めます。

そして重要なのは、ロボットの腕の目標が「ヘッドセットから見てコントローラがどこにあるか」という相対位置で決まることです。公式の既定は頭の向きを基準にする方式で、リリースノートにこう書かれています。

“use head-yaw-relative arm reference by default”

出典: unitreerobotics/xr_teleoperate リリースノート（v1.6）。この手順で使っているキットでは、向き基準だと操作中によそを向くと左右がズレるため、頭の位置を基準にする方式（arm_reference_mode="head_position"）に変更してあります。

どちらの方式でも、結果として次のことが起きます。

  • 手を動かしていなくても、頭が動けば腕の目標が変わります。振り向く・しゃがむ・歩く・立ち上がる、すべて腕の動きになります
  • 操作中は立ち位置と頭の高さをなるべく保つこと。見回したいときは、手を体の前で止めたまま、ゆっくり動かす
  • コントローラは顔の前〜やや横に保つこと。ヘッドセットのカメラから見えない位置（真横・背後・体で隠れる位置）に入ると追従が止まります

開始前の姿勢合わせについて、公式はこう書いています。次の手順09の注意と同じ趣旨です。

“Align your arm to the robot’s initial pose to avoid sudden movements at start.”

出典: unitreerobotics/xr_teleoperate README。終了時についても “position the robot’s arms close to the initial pose before pressing q to exit” と案内されています。

届いているかは、通信量を見れば分かります。

Quest からの通信を確認
ss -tn | grep :8012

この日の実測

192.168.0.247 から 7本の接続が確立
受信 約26.7 KB/秒（3秒で80KB）で継続中  ← 姿勢が流れている
09

追従を開始する

ここから腕が手に付いてきます

一言で：「いまから手の動きをまねして」という合図を出します。

合図を出す前に ── 腕の位置を合わせてください

追従が始まった瞬間、腕の速度上限が毎秒2ラジアンから30ラジアンへ上がります。つまりコントローラがロボットの手の位置から離れていると、その差を埋めるために腕が高速で動きます。

この日のロボットの腕は、両肘が約68〜70°曲がって前腕が前向き、右腕は内側に約47°捻れた姿勢でした。コントローラをその位置・向きに合わせてから開始しました。

合わせるのは手だけではありません。手順08で説明したとおり腕の目標は頭から見た手の相対位置で決まるので、開始したときの立ち位置と頭の高さを、そのまま保って操作を始めてください。合図を出した直後に屈んだり振り向いたりすると、手を動かしていなくても腕が動きます。

ターミナルで起動した場合は r を押すだけです。プログラムから送る場合は次のようにします。

追従開始（r に相当）
python - <<'EOF'
import zmq, uuid
ctx = zmq.Context.instance()
req = ctx.socket(zmq.REQ)
req.connect("ipc://@xr_teleoperate_data.ipc")
req.send_json({"reqid": str(uuid.uuid4()), "cmd": "CMD_START"})
print(req.recv_json())
EOF

成功のしるし

{'status': 'ok', 'msg': 'ok'}
heartbeat: {'START': True, 'STOP': False, 'READY': True}

10

止めるとき

安全な終了

一言で：両腕を初期姿勢へ戻してから、きれいに終了させます。

ターミナルで起動した場合は q を押します。Ctrl+C は使わないでください ── 腕が戻らないまま制御が切れます。

止める前に、腕を初期姿勢の近くまで戻しておくと安全です。公式ドキュメントも同じことを案内しています。

“position the robot’s arms close to the initial pose before pressing q to exit”

出典: unitreerobotics/xr_teleoperate README

終了（q に相当）
python - <<'EOF'
import zmq, uuid
ctx = zmq.Context.instance()
req = ctx.socket(zmq.REQ)
req.connect("ipc://@xr_teleoperate_data.ipc")
req.send_json({"reqid": str(uuid.uuid4()), "cmd": "CMD_STOP"})
print(req.recv_json())
EOF

送ると両腕が約5秒かけて初期姿勢へ戻ってから停止します。

この日の停止結果

応答 {'status': 'ok', 'msg': 'ok'}

rt/lowcmd     0.0 Hz        ← 誰も指令していない
腕mode=[0] 脚mode=[0]       ← 脱力（終了時の既定）
腕トルク 0.19 Nm / 脚 0.44 Nm ← 無負荷
帰還後  左肘 +76.1°  右肘 +63.2°  ← 初期姿勢付近へ復帰
teleop プロセス停止・ポート8012 解放

今回の構成では VR 内の緊急停止が使えません

右コントローラの A ボタンでの終了と、両スティック押し込みの緊急ダンピングは、別の起動方法（--motion）のときだけ有効です。この機体はそれが使えないため、止める手段は PC 側からの終了操作だけです。最終手段は電源です。

その代わり、スティックが歩行指令になることもありません。脚が勝手に踏み出す心配はない構成です。

なお終了するたびにモーターは脱力に戻ります。次に動かすときは手順6のダンピングからやり直してください。

この日つまずいたこと

すべて実際に起きたことです。同じところで止まったら、ここを見てください。

症状原因と対処

追加した安全装置

前日、テレオペ稼働中に有線 LAN が抜け、つなぎ直した瞬間に全29関節が一斉に最大の力で動いて大きな音が出るという事故が起きました。原因を調べて、再発しないようにしてあります。

なぜ起きたか

テレオペは起動時に全29関節の位置を記録し、そこへ戻そうとする力をかけ続けます。ケーブルが抜けている間も届かない指令を1秒250回送り続け、その間ロボットの手足は脱力して重力で垂れていきます。つなぎ直した瞬間、抜ける前の古い位置へ強い力で引き戻そうとして、全関節が同時に跳ねました。腕の速度制限も、比較する実測値が古いまま止まっていたため働きませんでした。

どう直したか

ロボットからの報告が0.2秒途切れたら、指令の送信を止めてプログラムを強制終了するようにしました。つなぎ直しても自動では復帰しません。復帰させると同じ事故が起きるからです。人が状態を確認してから起動し直す形にしてあります。

実機なしで動作を確かめられる試験も用意しました。

安全装置の動作試験（ロボット不要）
/home/ubuntu/miniforge3/envs/tv/bin/python tools/state_watchdog_selftest.py

試験結果

✅ 鮮度が新しい間は送信される（誤発火しない）
✅ 途絶で強制終了する（終了コード 1）
✅ 途絶を知らせるメッセージが出る
✅ 送信を止めてから落ちている
結果: PASS

いまテレオペ中に有線が抜けても、0.2秒でプログラムが止まるので跳ねません。

用語

ai（モーションコントローラ）
ロボットに最初から入っている歩行・バランス制御のプログラム。これが動いている間は指令の道を占有するため、テレオペと共存できません。
デバッグ状態
ai を止めて、外部から直接指令を送れるようにした状態。バランス制御は働かないので、必ず支持した状態で使います。
ダンピング（FSM 1）
モーターに電気が入り、動きに抵抗する状態。位置を保つわけではないので、手足は重力でゆっくり垂れます。テレオペを始めるにはこの状態が必要です。
ゼロトルク（FSM 0）
モーターの電気が切れて完全に脱力した状態。この状態では何を送っても腕は動かないのに、送信は成功と表示されます。
kp（ゲイン）
目標の位置へどれだけ強く引き戻すかの強さ。腕は80、脚は300に設定されています。数字が大きいほど、位置がずれているときに強い力が出ます。
Hz（ヘルツ）
1秒あたりの回数。ロボットの報告は1040 Hz、テレオペの指令は250 Hz です。
Nm（ニュートンメートル）
関節にかかっている力の大きさ。この日の最大は腕8.44、脚9.93で、どちらも余裕のある値でした。
