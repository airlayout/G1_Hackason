# 失敗ログ

このフォルダでの開発中に実際に起きた失敗と、その原因・反省・再発防止策を記録する。
新しい失敗が起きたら、下のテンプレートに沿って追記する。

## テンプレート

```
## YYYY-MM-DD: 失敗の一言タイトル

**何が起きたか**
（観測された事実。憶測ではなく実際に見えたことを書く）

**原因**
（コード上・手順上の根本原因）

**反省**
（なぜ事前に気づけなかったか。見落としていた前提は何か）

**再発防止策**
（実際にコード/手順をどう変えたか）
```

## 2026-09-30: テレオペ稼働中に有線LANが抜け、再接続した瞬間に全29関節が飽和トルクで跳ねた

**何が起きたか**
テレオペを起動したまま有線LANが抜けた。抜けている間は静かだったが、
**ケーブルを挿し直した瞬間に大きな音とともに全身の関節が一斉に動いた。**
その後ロボットの電源を落として安全を確保した。

**原因**
`xr_teleoperate` の送信ループ `_ctrl_motor_state()` に、**ロボットからの状態報告
（`rt/lowstate`）の鮮度チェックが無い。** そのため次の連鎖が起きた。

1. 起動時に全29関節の角度を取得し、そこを目標として固定する（脚 kp=300 / 腕 kp=80）
2. ケーブルが抜けている間も 250Hz で送信を続ける。届いていないことに気づかない
3. ロボット側は指令が途絶えて位置保持を失い、手足が重力で垂れる
4. 再接続した瞬間、**途絶前に凍結した目標**へ強い力で引き戻そうとして全関節が飽和

腕の速度制限 `clip_arm_q_target()` も効かなかった。比較対象の
`get_current_dual_arm_q()` が**途絶時点で凍結した実測値**を返すため、
「目標と現在値はほぼ同じ＝制限不要」と誤判定していた。

**反省**
「通信が切れたらどうなるか」を実機で動かす前に確認していなかった。
上流の実装を読めば watchdog が無いことは分かったはずで、
**実機の腕を動かすコードについては、正常系より先に異常系を読むべきだった。**

このキットは `replay_arm.py` には `--state-timeout` を用意しており、作者も概念は
認識していた。にもかかわらず teleop 側が素通しだったことを、流用時に確認しなかった。

**再発防止策**
`state-watchdog` パッチを作成し、上流（手元のクローン）へ適用した。
内容と検証結果は `real/quest3-g1-20261001/patches/state-watchdog.md`。

- `rt/lowstate` が **0.2秒** 途切れたら送信を止め、**プロセスを強制終了**する
- 再接続による自動復帰はさせない（復帰させると同じ事故が起きるため、意図的に fail-closed）
- 子プロセスも終了させる（残るとポート8012を掴んだままになり次回起動を妨げる）
- 実機なしで発火を確認できる自己テストを同梱（`tools/state_watchdog_selftest.py`）

**パッチ未適用の環境で実機を動かさないこと。**

## 2026-10-01: `rt/arm_sdk` が効かず、「送信成功なのに腕が動かない」状態になった

**何が起きたか**
モーションコントローラ（`ai`）が稼働中だったため、規格どおり `rt/arm_sdk` 経由で
腕を操作しようとした。制御権 `weight=1.00` を送り、指令も正しく出ているのに
**実測の変位が 0.0000 rad のまま**だった。エラーは一切出ない。

**原因**
**この機体が制御権の委譲に応じない。** 規格上は存在する経路だが、機体の
ファームウェア側が応答しない。コード側の問題ではなかった。

**反省**
「規格にあるから動くはず」という前提で進めかけた。エラーが出ない種類の失敗
なので、**実測で確かめるまで動いているか分からない**という点を軽く見ていた。

**再発防止策**
左肩を 0.05 rad（約3°）だけ動かして委譲が効くかを確かめる手順を、
実機を動かす前の標準ステップに組み込んだ（手順書の手順04）。
3°の動きで「機体の問題か、設定の問題か」を切り分けられる。

効かない場合は「`ai` を解除してデバッグ状態 + `rt/lowcmd`」が唯一の経路になる。

## 2026-10-01: ダンピングに入れても数十秒で切れ、テレオペ起動が弾かれ続けた

**何が起きたか**
`ai` を解除すると全モータがゼロトルクに落ちる。リモコンでダンピング（FSM 1）に
入れ直して `mode=1` を確認したが、**その約30秒後にテレオペを起動すると
「腕のモータが無効です」で起動が中断された。** 再確認すると `mode=0` に戻っていた。

**原因**
デバッグ状態では**指令が届かない時間が続くとモータが再び de-energize する。**
ダンピングを確認してから人が手動でテレオペを起動するまでの時間が、そのまま
デッドタイムになっていた。

**反省**
「ダンピングに入れた」を**状態**だと思っていたが、実際には
**指令を送り続けないと維持されない状態**だった。
人間とのやり取りの往復（確認 → 報告 → 起動）が原因になるとは考えていなかった。

**再発防止策**
`tools/watch_and_launch.py` を作成した。`rt/lowstate` を監視し、
**腕モータが `mode=1` になった瞬間（0.05秒以内）にテレオペを自動起動する。**
人の往復を挟まないので維持時間の制約を受けない。

実際、この方式に変えた1回目で成功した（ダンピング検出 71.7秒 → 即起動）。

## 2026-10-01: `quest_check` とテレオペがポート8012を奪い合い、起動に失敗した

**何が起きたか**
テレオペを起動したが、Quest 向けサーバが
`[Errno 98] address already in use ('0.0.0.0', 8012)` で起動できなかった。
テレオペ本体は動いているのに Quest からページが開けない状態になった。

**原因**
Quest の到達確認ツール `quest_check.py` が**同じポート8012を掴んだまま
動き続けていた。** 確認が終わった後も終了させていなかった。

**反省**
「確認ツールだから動かしっぱなしでも害はない」と考えていた。
**同じポートを使う以上、確認ツールと本番は排他**であることを意識していなかった。

**再発防止策**
手順書のトラブルシューティングに明記した。
Quest の到達確認は**テレオペを止めてから**行う。

## 2026-10-01: `ai` の解除が6回連続で失敗した（`status=3104`）

**何が起きたか**
`mode_check.py --release` を実行したところ、6回すべて `status=3104`
（送信は成功したが返事が来ない）で失敗し、「リモコン側で操作してください」と出た。

**原因**
モーションコントローラへのRPCが**散発的に無応答になる。**
恒久的な障害ではなく、タイミングによるもの。

**反省**
失敗メッセージが「リモコン側で操作してください」だったため、
**ソフトからは解除できない状態だと誤解しかけた。** 実際には同じコマンドを
もう一度流しただけで成功した。

**再発防止策**
手順書に「失敗しても1〜2回やり直す。失敗しても何も起きない」と明記した。
なお使用しているキットには既にリトライのパッチ（`motion-switcher-retry`、
タイムアウト 1.0 → 5.0 秒 + 6回試行）が入っており、**それでも失敗することがある。**

## 2026-10-01: 自動開始スクリプトが仕掛けた瞬間に発火し、合わせる間もなく追従が始まった

**何が起きたか**
ダンピング検出と同時に `CMD_START` を送るスクリプト（`tools/autostart.py`）を
仕掛けたところ、**起動した瞬間（`t=0.0s`）に発火して追従が始まった。**

```
ARMED  リモコンでダンピングを入れた瞬間に CMD_START を送ります
STATE t=   0.0s arm_mode=[1]      ← この時点で既に条件成立
DETECT t=0.0s -> CMD_START 送信
REPLY {'status': 'ok'}
```

**原因**
仕掛けた時点で**すでにモータが `mode=1`（通電中）だった。**
「ダンピングが入るのを待つ」つもりの条件が、最初から成立していた。

**反省**
「イベントを待つ」スクリプトを書いたつもりだったが、実際には
**「条件を満たしたら実行する」**スクリプトだった。条件が既に真なら即実行される。
仕掛ける前に現在値を確認していなかった。

実機が動く操作では、この違いが安全性に直結する。今回は指令と実測の偏差が
3.1° だったため実害はなかったが、コントローラが腕から離れていれば
**速度上限 30 rad/s で腕が急に動いていた。**

**再発防止策**
実機を動かすトリガを仕掛ける前に、**必ず現在の状態を測ってから仕掛ける。**
条件が既に成立している場合は、仕掛けずに人へ知らせる。

`real/quest3-g1-20261001/README.md` の `autostart.py` の項にも注意書きを追加した。

## 2026-10-01: `pkill -f` が自分自身のシェルを巻き込んで落とした

**何が起きたか**
後片付けのつもりで `pkill -f "teleop_hand_and_arm"` を実行したところ、
**コマンドを実行しているシェル自身が落ちた**（終了コード 144）。

**原因**
`pkill -f` は**コマンドライン全体**にパターンを照合する。
実行中のシェルのコマンドラインにはそのパターン文字列がそのまま含まれるため、
自分自身にマッチして kill した。

`[t]eleop_hand_and_arm` のようにブラケットで囲む回避策を使っても、
**同じコマンド内の別の場所にその文字列が平文で出ていれば**やはりマッチする。

**反省**
よく知られた罠だが、ワンライナーで「停止してから起動する」とまとめたときに
踏みやすい。**停止と起動を1つのコマンドに混ぜたこと**が根本的な問題だった。

**再発防止策**
後片付けに `pkill -f` を使わない。`pgrep` で確認し、必要なら PID を指定して kill する。
停止と起動は別のコマンドに分ける。
