# 実証1: Quest 3 で G1 の両腕を追従させる（2026-10-01）

**結果: 成功。** Meta Quest 3 のコントローラの動きに、G1 の両腕 14 関節が追従することを実機で確認した。

| | |
|---|---|
| 日付 | 2026-10-01 |
| 機体 | G1 29自由度（`mode_machine=5`） |
| 設置 | **吊り下げ**（足は接地）。バランス制御を止めるため支持が必須 |
| XRデバイス | Meta Quest 3（コントローラ入力） |
| 操作PC | Ubuntu 24.04 / Python 3.10（conda環境 `tv`） |
| 接続 | 有線（ロボット制御）+ 無線（Quest） |

## 何を検証したか

**テレオペの基本動作が成立するか。** 具体的には次の4つ。

1. 操作PCからG1の制御権を取れるか
2. テレオペが起動し、Quest から接続できるか
3. コントローラの動きに腕が追従するか
4. 安全に停止できるか

**すべて確認できた。** 実測値は [`measurements.md`](measurements.md)。

## 使った経路（この機体での唯一の経路）

```
ai を解除してデバッグ状態へ  →  リモコンでダンピング  →  rt/lowcmd で腕を駆動
```

規格上は `ai` を止めずに腕だけ借りる `rt/arm_sdk` という近道があるが、
**この機体は制御権の委譲に応じなかった**（指令 +0.05 rad に対し実測 0.000 rad）。
そのため上記が唯一の経路になる。詳細は [`../../docs/findings-20261001.md`](../../docs/findings-20261001.md)。

## このフォルダのツール

いずれも**今回のために書いたもの**。`g1-starter-kit` 本体には含まれない。

| ファイル | 用途 |
|---|---|
| `tools/watch_and_launch.py` | `rt/lowstate` を監視し、**ダンピングを検出した瞬間に teleop を起動する**。人の往復を挟むとダンピングが切れるため |
| `tools/autostart.py` | 同様に、ダンピング検出と同時に `CMD_START`（追従開始）を送る |
| `tools/state_watchdog_selftest.py` | `state-watchdog` パッチが発火するかを**実機なしで**確かめる |
| `patches/state-watchdog.md` | 上流へ当てた安全パッチの内容・根拠・検証結果 |

### `autostart.py` を使うときの注意

**仕掛ける前に必ずモータの現在状態を確認すること。**
既に `mode=1`（通電中）だと**仕掛けた瞬間に追従が始まる**。
今回それが起きた（偏差 3.1° だったため実害はなかったが、ズレが大きければ腕が速く動く）。

## キー操作をプログラムから送る仕組み

`teleop.sh` は本来ターミナルで `r`（開始）/ `q`（終了）を押して操作する。
しかし自動化のため、`--ipc` オプションでプログラムから指示を送る形を使った。

ZMQ の UNIX ソケット `ipc://@xr_teleoperate_data.ipc` に JSON を投げる。

| コマンド | キー相当 | 動作 |
|---|---|---|
| `CMD_START` | `r` | 追従開始 |
| `CMD_RECORD_TOGGLE` | `s` | 記録の開始／保存 |
| `CMD_STOP` | `q` | 終了（両腕が約5秒で初期姿勢へ戻る） |

**`CMD_STOP` は安全に止められる唯一の手段**なので、この仕組みは安全上も有効だった。
`--motion` 無しの構成ではVR内の緊急停止（右Aボタン・両スティック押し込み）が
使えないため、停止手段は操作PC側しかない。

## 起動コマンド

```bash
cd ~/g1-starter-kit

# 1. 疎通と機体構成（ロボットは動かない）
./scripts/preflight.sh

# 2. 指令経路とモータ状態（ロボットは動かない）
~/miniforge3/envs/tv/bin/python tools/mode_check.py --iface enp129s0

# 3. arm_sdk が効くか（左肩が約3°動く）
~/miniforge3/envs/tv/bin/python tools/armsdk_probe.py --iface enp129s0 --yes

# 4. ai を解除（バランス制御が止まる。支持必須。失敗したら1〜2回やり直す）
~/miniforge3/envs/tv/bin/python tools/mode_check.py --iface enp129s0 --release

# 5. ダンピング検出と同時に teleop を起動
setsid nohup ~/miniforge3/envs/tv/bin/python -u watch_and_launch.py teleop.log \
  > watch.log 2>&1 < /dev/null &
#   → この状態でリモコンのダンピング（FSM 1）を入れる

# 6. Quest をつなぎ、モータ状態を確認してから CMD_START
```

## 残った課題

| 課題 | 内容 |
|---|---|
| **通電の維持** | モータの通電はリモコンのFSMでしか維持できず、**時間とともに切れる**。teleop が `mode=1` を 246Hz で送っていても実測は `mode=0` のままだった（12秒観測）。作業のたびにダンピングを入れ直す必要がある |
| **映像が無い** | ヘッドセットにロボット視点の映像が出ない。PC2 の画像サービスを起動していないため。G1 を直接目で見ながらの操作になる |
| **VR内の緊急停止が無い** | `--motion` を使えないため、右Aボタン・両スティック押し込みが無効。停止手段は操作PC側のみ |
| **watchdog の実機検証** | `state-watchdog` パッチの発火は自己テストで確認済みだが、**実機で有線を抜いての確認は未実施** |
| **記録・再生** | 今回は追従のみ。記録（`--record`）と再生は未着手 |

## 次にやること

1. **`state-watchdog` の実機検証** — テレオペ中に意図的に有線を抜き、0.2秒で落ちること、再接続しても無反応なことを確認する
2. **記録と再生** — 追従中の動きを記録し、あとから再生する（領域スコープの段階2）
3. **映像つき操作** — PC2 の画像サービスを立ち上げ、ロボット視点を見ながら操作する
