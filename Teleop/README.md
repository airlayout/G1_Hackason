# Teleop（遠隔操作）

人がXRデバイス等でG1を直接操作する機能全般。`Voice/`・`Perception/`等と同じ
「機能ドメインごとにトップレベル1つ」の構成に合わせて新設。

遠隔操作は**操作者・ヘッドセット・実機の相互作用そのものが対象**で、sim側で
検証しても実機の制御権・モータ状態・追従遅延といった本質的な問題が再現しない。
そのため`sim/`は作らず、`real/`配下に実証ごとのフォルダを置く。

## スコープ（段階順）

| 段階 | 内容 | 状態 |
|---|---|---|
| 1. 腕の追従 | XRコントローラの動きにG1の両腕が追従する | **実機で確認済み**（2026-10-01） |
| 2. 教示と再生 | 追従中の動きを記録し、あとから再生する | 未着手 |
| 3. ハンド | Inspire / Dex3 ハンドの開閉を含めた操作 | 未着手 |
| 4. 映像つき操作 | ロボット視点の映像をヘッドセットに出す | 未着手（PC2の画像サービスが必要） |
| 5. 歩行を含む操作 | 腕だけでなく移動も遠隔で指示する | 未着手 |

## 今後プロジェクトを追加するときのルール

**実証（プロジェクト）ごとに `real/<対象>-<YYYYMMDD>/` を1つ作る。**
日付は実機で動かした日。既存フォルダは書き換えず、新しく作る。
「いつ・何で・どこまで動いたか」が後から辿れることを優先する。

各プロジェクトフォルダに最低限これを置く:

- `README.md` — 何を検証し、どこまで動き、何が残ったか
- `measurements.md` — 実測値。**推測と実測を混ぜない**
- `tools/` — その実証のために書いたスクリプト

**領域をまたいで再利用するものは `docs/` か、安定したら `Teleop/` 直下へ出す。**
実証フォルダは当時の記録として凍結し、育てない。

**失敗は必ず `FAILURES.md` に書く。** 遠隔操作は実機でしか分からない失敗が多く、
同じところで止まる人が必ず出る。

## 既知の注意点

実機を動かす前に [`docs/findings-20261001.md`](docs/findings-20261001.md) と
[`FAILURES.md`](FAILURES.md) を読むこと。特に重要なもの:

- **この機体では `rt/arm_sdk`（制御権の委譲）が効かない。** 実測で指令 +0.05 rad に対し
  変位 0.000 rad。よって「`ai` を解除してデバッグ状態 + `rt/lowcmd`」が唯一の経路になる
- **`ai` を解除すると全モータがゼロトルクに落ちる。** 復帰はリモコンのダンピング（FSM 1）
  のみ。指令側の `motor_cmd[].mode=1` では有効にならない
- **ダンピングは数十秒で切れる。** 指令が届かない状態が続くと再び脱力する。
  検出と同時に起動する必要がある（`tools/watch_and_launch.py`）
- **通信が切れたまま再接続すると全29関節が飽和トルクで跳ねる。** 対策パッチを
  上流へ当てている（`patches/state-watchdog.md`）。**パッチ未適用の環境で実機を動かさない**
- **バランス制御が止まるので、必ず吊り下げか座位で支持する**

## 安全

**これは実機の腕を動かす機能である。** 腕は人を傷つけられる速度と力を持つ。
手順書の安全記述を省略しないこと。要点:

- G1 を吊り下げまたは座位で支持する。立たせたまま行わない
- 腕の可動範囲に人と物を置かない
- 電源をすぐ切れる位置に人を配置する
- 初めてのときは2人以上で行う
- 追従開始の瞬間に腕の速度上限が 2 → 30 rad/s へ上がる。開始前に必ず姿勢を合わせる

## テストについて

このフォルダには `tests/run_tests.sh` を置いていない。CI の一覧には
「検証されていない」と出るが、それが実態として正しい。

遠隔操作の検証は**実機・ヘッドセット・操作者が揃って初めて成立する**ため、
CI 環境（実機なし・XRなし・`unitree_sdk2py` なし）で意味のある自動テストが書けない。
機械的に確認できるものは実証フォルダの `tools/` に自己テストとして置き、
手元の環境で実行する形にしている。
