# 実機プレイ用 管理ダッシュボード 要件（2026-11-05 ヒアリング版）

2D 潜入ゲーム（`StealthGame2D`）を、実機の G1 と Pepper で遊べる状態にするための管理ダッシュボードの要件。
ヒアリングで決まったことと、未確定のこと（推測で埋めていない）を分けて書く。

## 1. ゴール

- 実際の人が現場を歩き、G1 と Pepper に見つからないように START → TARGET → START を目指す。
- 運営が **指示送信** と **状況把握** を 1 つの GUI で行う。
- 前提: 他メンバーが Pepper・G1 の制御の調査を、ある程度終えている。ここでは使える部品として統合する。

## 2. ヒアリングで決まったこと

| 項目 | 決定 |
|---|---|
| プレイヤー | 実際の人が現場を歩く |
| G1 の動き | 直線を行ったり来たりするだけ。ずれは小さい見込み。ずれ防止に **床にラインテープなどの目印を置いてよい** |
| G1 の制御 | Entame 内で簡易に歩かせる（SDK の速度指令。地図・ナビは使わない） |
| Pepper の動き | その場で首を振る |
| 見つかった判定 | 実機カメラ映像（YOLO）。G1 は `g1-detection-spec.md`、Pepper は `pepper-detection-spec.md` |
| 人の位置 | **取らない**。検知されたらダッシュボードに表示すればよい |
| 運営 | 運営 1 人が PC で操作。スマホでも見られる |
| スマホ | 専用のスマホ画面にボタンを置く。**プレイヤーが持ち、自分で押す** |
| 現場 | 10m × 10m 程度 |
| ネットワーク | G1・Pepper・操作 PC・スマホは全部同じ LAN（Wi-Fi ルーター 1 台） |
| 進め方 | 段階的（Pepper 単体 → G1 追加 → ゲーム進行を統合） |

## 3. 画面構成

### 3.1 運営ダッシュボード（PC）

- **マップ**: ステージ JSON の START / TARGET / 壁を描く。G1 の巡回ライン、G1 の推定位置、G1 と Pepper の視野の扇形（Pepper は首振りに合わせて動かす）を重ねる。
  - 人の位置は出さない。
  - G1 の推定位置は、指令速度と経過時間による推定値であることを画面に明記する（実測ではない）。
- **状態表示**: ゲーム状態（待機 / プレイ中 / GAME OVER / CLEAR）、経過時間、G1 と Pepper の接続状態、G1 の動作モード、最終受信時刻。
- **検知表示**: どちらのロボットが、いつ、人を検出したか。検出したカメラ映像（枠つき）を見られる。
- **操作ボタン**: ゲーム開始 / 終了 / リセット、G1 の巡回開始 / 停止、Pepper の首振り開始 / 停止、**緊急停止**。
- **ログ**: イベント（開始・検知・ボタン押下・停止・通信断）を時刻つきで並べる。

### 3.2 プレイヤー用スマホ画面

- ボタン: 「TARGET を取った」「START に戻った」。
- 表示: 見つかったとき（検知結果の表示、必要なら振動）、ゲーム状態。
- 操作は最小限にする（大きなボタン、誤タップ防止）。

## 4. 機能要件

### 4.1 指示送信

| 対象 | 指示 | 備考 |
|---|---|---|
| G1 | 巡回開始 / 停止 / 緊急停止 | 前進 → 旋回 180° → 前進の往復。後退は使わない |
| Pepper | 首振り開始 / 停止、振り幅・速度の設定 | 既存の `pepperapp`（NAOqi 9559）を使う |
| ゲーム | 開始 / 終了 / リセット | ステージはエディタで作った JSON を選ぶ |
| G1 | **リセット（= 初期位置に戻す）** | 巡回の初期位置（往復の端のテープ位置）へ戻す。後退は使えないため、旋回 → 前進で戻る。実行中は停止ボタンを常に押せる。ゲーム状態の初期化も兼ねる（2026-11-07） |

### 4.2 状況把握

- ロボットの接続・生存確認（ハートビート）。
- カメラ映像の取得と YOLO 検出（既存 `detector.py` を再利用）。
- ゲーム状態の一元管理（状態機械）。イベント履歴を残す。

### 4.3 ゲーム進行の確定

- **安全停止（1 m）が働いたときは GAME OVER にする。運営が再開する**（2026-11-05 ユーザー指示）。再開は運営のボタン操作のみとし、自動では再開しない。

- TARGET 取得・START 復帰は、プレイヤーがスマホのボタンで申告する。
- **救出ルール（`win-conditions.md` の④）でも、ダッシュボードに新しい操作や表示は足さない**（2026-11-07 ユーザー回答）。LOVOT が通常モードに切り替わったことはシステムに伝えられない。運営の「救出」ボタンは作らない。マップには TARGET の初期位置だけを出し、LOVOT の位置は出さない。プレイヤーは同じスマホのボタンで申告する。救出の成否と、LOVOT が一緒に戻ったかは、システムでは判定しない。**LOVOT を連れて戻ったかは、プレイヤーが goal（「START に戻った」）をタップすることで確定する**（運営は確かめない。2026-11-07 ユーザー回答）。
- 「見つかった」は YOLO の検出結果。ダッシュボードとスマホに表示する。
- 「見つかった」は YOLO が自動で判定し、確定したら**即 GAME OVER**にする。運営の確定は挟まない（2026-11-05 ユーザー指示）。判定の条件は `g1-detection-spec.md` と `pepper-detection-spec.md` に従う。
- 誤検知は、運営が「再開」で復帰する。あとから確認できるよう、検知した瞬間の画像 1 枚と検出結果（信頼度・継続時間）をログに残す。

### 4.4 G1 の位置ずれ対策（床の目印）

- 往復の両端と中央に、床にラインテープを貼る。
- 使い方は 3 案。検証してから選ぶ（どれが効くかは未測定）。
  1. 運営が目視で確認し、ずれたら手動で停止して位置を戻す（実装が最も軽い）。
  2. 一定回数の往復ごとに、運営が「位置リセット」を押す。
  3. G1 のカメラでテープを検出し、端を判断する（画像処理が必要）。
- 往復の前進距離は、実測の誤差（指令の約 76% しか進まない実績がある）を見て、距離ではなく**時間 + 目印**で管理する案も検討する。

ボタン押下時の事前チェック（リセット・巡回開始・巡回停止）は `preflight-design.md` に定義した。

## 5. 安全要件（`docs/safety.md` に従う。ダッシュボードで緩めない）

- ゲームの判定と安全停止は別系統にする。ダッシュボードの緊急停止は **追加の停止手段**であり、G1 のコントローラ保持者による停止を置き換えない。
- G1 のコントローラ保持者は、運営とは別の人にする。
- 通信断（1 秒）で G1 は停止する。ダッシュボードのハートビートが切れたときも停止側に倒す。
- 人との距離 **1 m** で停止する（2026-11-05 ユーザー指示）。幾何的な停止は別途ソフトで実装し、カメラ検出に依存しない系統を残す。
  - `docs/safety.md` の絶対規則 2 と開始前チェックリストは 1 m に更新済み（2026-11-05）。
  - 他の文書（`g1-detection-spec.md`、`proposal/steal-the-eye-deck.html` など）には 2.5 m の記述が残っている。検知の最小距離と安全距離は別の話のため、どこまで変えるかは別途決める。
  - 静止指令でも G1 は約 0.04 m/s 漂う（実測）。1 m にするぶん、停止距離の余裕が減る点に注意する。
- G1 を人に向かって歩かせない。ただし巡回の前進（直線の往復）は許可し、人の方が G1 の前に来た場合は仕方ない（safety.md 規則 1）。その場合は安全距離で止める。
- 旋回は 1.0 rad/s 以下。クランプを迂回する経路を作らない。
- プレイヤーは歩く（走らない）。
- 動作モードは SDK の `sport_mode` / `LocoClient` を使う。lerobot（カスタム ONNX）とは排他で、切り替え時は転倒リスクがあるため、ダッシュボードに切り替えボタンを置かない。

> 要確認: 「G1 が直線を往復する」ことと、safety.md の「人に向かって歩かない」の整合。
> 往復ラインの端でプレイヤーと同じ空間にいるため、ラインの位置と、プレイヤーが通れる範囲を現場の配置図で確認する。

## 6. 未確定の項目（実装前に決める）

1. 「再開」の意味。GAME OVER を解除して「準備」へ戻す（プレイヤーは START へ、G1 は初期位置へ）のか、その場から続けるのか。
2. 10m × 10m の現場での G1 の往復ラインの位置と長さ（実測していない）。
3. Pepper の設置位置と向き、首振りの角度範囲と速度（28.6°/s は仮値）。
4. Pepper の映像は有線前提（有線 VGA で約 29.7fps、Wi-Fi は低速）。同じ LAN に Wi-Fi 経由で参加させた場合、映像の遅れが許容できるか。
5. ダッシュボードの形（Web か、Streamlit など）。既存の `devserver.py` を拡張するか、別サーバーにするか。
6. スマホ画面の入口（URL を開く方式か、QR コードか）。
7. 実機がいつ使えるか、デモの日程。
8. G1 への経路は **PC2 にサーバーを置く案（`preflight-design.md` §7 の D）で進める**（PC2 にコードを置く・Wi-Fi で届く、は確認済み）。未確認は PC2 の余力（Web サーバーと YOLO を載せて G1 の動きが乱れないか）。実機で測る。
9. 救出ルールのスマホのボタンの文言をルールで変えるか（「TARGET を取った」→「救出した」案）。
10. 人との距離 1 m の測り方。LiDAR を安全停止に、Web カメラを検知に使う案（LiDAR が安定して取れるかの実機試験が先。`preflight-design.md` §5 の 2）。

決定済み（2026-11-05〜07）: リセット = 初期位置に戻す／緊急停止は G1 と Pepper の両方を止め、ゲームも GAME OVER／人との距離は Web カメラ・LiDAR のどちらを使ってもよい（死角と別系統でない点も許容）／G1 の検知の最小距離は 1 m／YOLO の閾値の調整 UI は不要／スマホの申告の取り消しは不要。

## 7. 段階計画（案）

| 段階 | 内容 | 完了の目安 |
|---|---|---|
| 0 | 設計の確定（本書の未確定項目を決める）、通信方式の決定 | §6 の 1〜5 が決まる |
| 1 | Pepper 単体: 接続・首振り開始 / 停止・映像と検出をダッシュボードに表示 | ダッシュボードから Pepper を動かし、検出が見える |

各段階で実機確認を行い、**動作を確認するまで「できた」と書かない**。

## 8. 非機能要件

- 同じ LAN 内のみ。外部への送信なし。認証は現場の LAN 前提（必要なら簡易パスワード）。
- ダッシュボードが落ちても、G1 はタイムアウトで停止する。
- 映像と検出結果は、必要なときだけ保存する（個人が映る。保存する場合は事前に参加者へ伝える）。
- 状態遷移と指示は、すべてログに残す（再現・事後確認のため）。

### 11.1 ヒアリングの決定との整合

- **G1 の直線往復**: 一致する。巡回は 2.4 m の直線 1 本だけなので、テープは往復の両端と中央に貼れば足りる。
- **Pepper**: カメラ役としてそのまま使える。視野 57.2° は Pepper の上部カメラの画角（57.2°）と同じ。ただし Pepper の置き場所は壁の外側（通路の北側 約 1 m）になる。人が近すぎると画角に入らない可能性があるため、現場で確認する。
- **壁**: 4 枚を現場に置く。位置はテープで床に出す。素材と置き方は未確認。

### 11.2 要確認: G1 の停止距離（1 m）とこの配置

停止距離は 1 m に変更された（§5）。JSON の座標から計算すると、G1 の北端（y = 5.8 m、x ≈ 4.6 m）から 1 m 以内は、
通路（y = 4.1〜5.7 m）のうち **y > 4.8 m、x = 3.6〜5.6 m の範囲**にあたる。
- 通路の北側の約 0.7 m（y = 4.1〜4.8 m）は 1 m の外なので、プレイヤーはそこを通れば G1 を止めずに通過できる。ただし幅 0.7 m と狭い。
- 通路の中心（y ≈ 4.9 m）を歩くと、G1 が北端にいるときに停止する（約 0.9 m）。
- G1 は約 12 秒で 1 往復する。北端付近にいる時間は限られるが、停止の判定は位置で決まり、時間では決まらない。

停止したときは GAME OVER になり、運営が再開する（§4.3）。つまり、通路の中心を歩くと G1 が停止して GAME OVER になりうる。このステージ設計が狙いどおりかを確認し、そうでなければ次のどれかで調整する。
- G1 の巡回を南へずらす（ステージ JSON の巡回ルートを変更して再保存）。
- プレイヤーが G1 に近づけない範囲を、テープで床に示す。

> 要確認: safety.md は「反応は旋回のみ」「前進はずれが大きい。人に向けない」としている。
> この巡回は G1 が北向きに前進して通路側へ近づく動きを含む。「人に向かって歩かない」との整合を、安全担当と確認する。

### 11.3 現場で測ること（未測定）
