# ボタン押下時の事前チェック（プリフライト）設計

ダッシュボードのボタンを押したときに動くスクリプトを設計するための定義書。
対象は **リセット・巡回開始・巡回停止**の 3 つを、**G1・Pepper・両方**について。
上位の要件は `dashboard-requirements.md`、安全は `safety.md` に従う（ここで緩めない）。

作成: 2026-11-05。実装はまだ無い。実機では何も動かしていない。

## 0. 読み方（実測と推測を分ける）

| 印 | 意味 |
|---|---|
| ✅ | リポジトリの既存コードで確認できる（出典を付ける） |
| ❓ | 未確認・未実測。推測で埋めていない。実機で確かめるまで仮置き |
| 仮 | この文書での提案値。根拠となる実測が無い |

## 1. 共通の枠組み

### 1.1 チェックの結果

1 つのチェックは次の形を返す（スクリプトの入出力の型）。

```
Check:   id, target(G1|Pepper|Common), severity(BLOCK|WARN|MANUAL), timeout_s
Result:  status(pass|fail|unknown), detail(人が読む文), measured(測った値), at(時刻)
```

- **BLOCK**: 通らなければ実行できない（ボタンは押せても実行されず、理由を出す）。
- **WARN**: 運営が理由を読んで「実行する」を選べば実行できる。
- **MANUAL**: 機械で測れない項目。運営がチェックを入れる。入れるまでは BLOCK と同じ。
- **unknown（測れなかった・時間切れ）は pass にしない**。BLOCK なら失敗扱い。

### 1.2 実行の流れ（開始系のボタン共通）

1. ボタンの二重押しを防ぐため、操作中ロックをかける（C-03）。
2. 該当するチェックを**並列**で実行する。各チェックの時間切れは 2 秒（仮）。
3. 結果の一覧を画面に出す。BLOCK の失敗と未チェックの MANUAL が 1 件でもあれば、ここで中止。
4. 通ったら、**実行の直前**に「接続」「lowstate の鮮度」「緊急停止ラッチ」だけ再確認する（結果が古いと危ないため。鮮度は 5 秒（仮））。
5. 実行して、完了確認を取る。結果はすべてログに残す。

### 1.3 例外: 停止系は「止める」を絶対に邪魔しない

- **巡回停止・緊急停止にはブロックするチェックを置かない。**押せば必ず止めに行く。
- 停止系のチェックは「状態を表示するだけ」。失敗しても停止の送信は止めない。
- 停止の送信が失敗したら、リトライし、それでも駄目なら画面に赤く出して**コントローラ保持者に知らせる**（運営の停止は追加手段であり、コントローラの停止を置き換えない）。

## 3. ボタン別の定義

凡例: 表の ● = その行のチェックを実行、○ = 情報表示のみ（結果で止めない）、空欄 = 実行しない。

### 3.1 巡回開始（G1 の巡回 ＋ Pepper の首振り）

許す状態: 準備（開始前チェック済み）、または再開直後。

| チェック | G1 | Pepper |
|---|---|---|
| C-01〜C-04 | ● | ● |
| C-05, C-06 | ● | |
| P-01〜P-06, P-08 | | ● |
| P-07 | | ● |
| G-01〜G-04, G-06〜G-09 | ● | |
| G-05, G-10, G-11 | ● | |

実行手順（チェックが全部通ったあと）:

1. **Pepper を先に始める**（失敗しても人は危なくないため）。
   1. `ALBasicAwareness` を停止（勝手に頭を動かさない）。既存コードは接続時に停止する ✅
   2. 首振りのスレッドを開始。目標角度を順に `angleInterpolationWithSpeed` で送る ✅
   3. 完了確認: 3 秒以内に頭の角度が変化していること（`getAngles` の差）。
2. **G1 を始める**。
   1. 巡回ループを開始: 前進（`SetVelocity(vx,0,0,duration)`）→ 停止 → 180° 旋回（ω ≤ 1.0 rad/s）→ 前進、を繰り返す。
   2. 速度指令は **0.5 秒以下の短い指令を出し続ける方式**にする（既存の試験ハーネスの上限が 0.5 秒 ✅）。ダッシュボードが落ちて指令が止まると、G1 は指令の期限切れで止まる想定。**この期限切れの停止は実機で未検証❓**
   3. 完了確認: 最初の指令の戻り値が 0。0 以外ならすぐ `StopMove`、**再送しない**（既存方針 ✅ `MAPLESS_WANDER_G1_VALIDATION.md`）。
3. 状態を「巡回中」にして、ログに残す。
4. **途中の失敗の扱い**: G1 の開始に失敗したら、Pepper の首振りも止めて「準備」に戻す（片方だけ動くゲームは成立しない）。

### 3.2 巡回停止（G1 の巡回 ＋ Pepper の首振り）

許す状態: 巡回中、または GAME OVER 直後（停止が残っていないかの確認用）。**ブロックするチェックは無い**（§1.3）。

| チェック | G1 | Pepper |
|---|---|---|
| C-03 | ○ | ○ |
| G-09, P-08（動作中か） | ○ | ○ |
| その他 | | |

実行手順:

1. **G1 を先に止める**（同時に送る。送信の順番だけ G1 が先）。
   1. 巡回ループを止める（これ以上、速度指令を出さない）。
   2. `StopMove()` を送る。戻り値が 0 でなければ、**0.2 秒（仮）あけて最大 3 回（仮）まで再送**。停止は安全側の操作なので、開始と違って再送を許す。
   3. 立ったまま止める。**脱力（Damp）系の API はダッシュボードに置かない**（倒れるため）。
2. **Pepper を止める**。
   1. 首振りのスレッドに停止を伝え、次の目標を送らない。
   2. 注意: `set_head` は**頭が着くまで戻らない**（ブロッキング ✅）。振り幅 90° を 28.6°/s（仮値）で動かすと**片道約 3.1 秒**。このままでは停止指示の反映が最大約 3 秒遅れる。即時停止が必要なら ALMotion の動作中断 API を使う（**どれを使うか❓、実機で確認**）。
   3. 頭は止めた位置のまま。`ALBasicAwareness` は再開しない（ゲーム中に勝手に動かさないため。再開は接続を閉じるとき ✅）。
3. 完了確認: G1 は `StopMove` の戻り値 0、Pepper は頭の角度が 1 秒間動かない。
4. 確認が取れない場合は、赤く「停止を確認できない」を出し、コントローラ保持者に伝える。

### 3.3 リセット（= G1 を初期位置に戻す ＋ 次のプレイの準備）

2026-11-07 のユーザー指示で、**リセット = 初期位置に戻す**。1 つのボタンにまとめる。
**G1 が動く操作**なので、巡回開始と同じ水準の安全チェックを通す。

許す状態: 準備、CLEAR。GAME OVER と安全停止のあとは、先に「再開」でラッチを解除してから押す（仮・§5 の 4）。
**PLAYING 中は押せない**（先に「ゲーム終了」）。

| チェック | G1 | Pepper |
|---|---|---|
| C-01〜C-04 | ● | ● |
| C-05, C-06 | ● | |
| G-01〜G-04, G-06〜G-09 | ● | |
| G-11（進む先に人・物がない） | ● | |
| G-05 | ● | |
| P-01, P-03, P-08 | | ● |
| G-10（初期位置にいる） | **実行後に**確認 | |

- C-02 は BLOCK。**1 m の安全停止の直後は、人がまだ近くにいる可能性が高い。**G-07 が「1 m 以内に人なし」を返し、運営が C-06 を確認するまで動かさない。
- G-10 は他のチェックと逆で、実行**前**ではなく実行**後**の MANUAL 確認（着いたかどうかを見る）。

実行手順:

1. 巡回・首振りが止まっていることを確認。止まっていなければ**中止**し、「先に巡回停止」と出す。
2. **G1 を初期位置へ戻す**（後退は使わない）。
   1. 巡回ループの記録（現在の向きと、最後に折り返してからの前進時間）から、戻る向きと時間を計算する。
   2. 初期位置と逆向きなら、180° 旋回（ω ≤ 1.0 rad/s）→ 前進。
   3. 戻ったら、巡回の最初の向きへ旋回して止まる。
   4. **戻り量の誤差は未測定❓**（位置を測る手段が無い。指令の約 76% しか進まない実績がある）。時間で戻すので、行き過ぎの恐れがある。端の手前で必ず止まるよう、戻る時間は少なめに見積もり、足りなければ運営が目視で補う案を検討する。
   5. 戻っている間も、**停止ボタンとハートビート監視を有効**にする。1 m 以内に人が入れば止まる（G-07）。
3. 着いたら G-10（初期位置にいるか）を運営が目視で確認。ずれていたら、コントローラ保持者に手動で直してもらう。
4. ゲーム状態を初期化: 経過時間、TARGET・START の申告、検知の記録、GAME OVER の表示を消す。
5. Pepper: 頭を正面（HeadYaw 0、HeadPitch は初期値）へ。速度は 0.3 以下 ✅。戻せなくても失敗にはせず警告のみ。
6. 手動チェック（C-05, C-06, G-05, G-10, G-11）を**全部未チェックに戻す**（次の開始前に毎回確認させるため）。
7. スマホ画面を「待機」に戻す。ログに残す。

## 4. 「両方」の組み合わせ規則と緊急停止

| 場面 | 規則 |
|---|---|
| 開始系のチェック | G1・Pepper を並列で実行し、1 画面に出す。どちらかの BLOCK 失敗で全体中止 |
| 開始の順序 | Pepper → G1。G1 の失敗で Pepper も戻す |
| 停止の順序 | G1 → Pepper（同時送信。G1 を先に） |
| リセット | 両方が止まっているときだけ。G1 が動くので G1 の安全チェックを通す |
| 片方だけの操作 | 単体試験の段階 1・2 のために、G1 のみ・Pepper のみの実行も残す |

### 緊急停止（確定: G1 と Pepper の両方を止める）

- チェックなし・確認ダイアログなし。どの状態でも押せる。
- G1: 巡回ループ停止 → `StopMove`（失敗時は再送）。Pepper: 首振り停止。
- ラッチする。解除は運営の「再開」だけ（自動では戻らない）。
- **ゲームも GAME OVER にする**（2026-11-07 ユーザー指示。安全停止 1 m と同じ扱い）。スマホには「運営が停止しました」と出す。
- 追加の停止手段であり、コントローラ保持者の停止を置き換えない。

## 5. 未確定・要実測

1. **ダッシュボードから G1 へどう届くか**。既存の G1 制御コードは G1 内部の PC2（eth0・192.168.123.164）上でだけ動く作りで、Desktop は Wi-Fi/SSH で PC2 を操作するだけ、Desktop から DDS は行わない、と決めてある ✅（`G1_PC2_RUNTIME.md`）。PC2 に新しいスクリプトや venv を作らない方針もある。ヒアリングでは「全部同じ LAN」だったが、内部 .164 へ Wi-Fi 経路があるとは仮定していない ✅（同上）。選択肢は §7。
2. **人との距離 1 m の測り方**。Web カメラ・LiDAR のどちらを使ってもよい（2026-11-07 ユーザー指示）。死角と「検知と安全停止が同じカメラ」は許容済み。案は次のとおり。
   - **安全停止 1 m は LiDAR、「見つかった」の検知は Web カメラ（YOLO）**に分ける案。LiDAR はカメラとは別系統になり、要件書 §5 の「カメラ検出に依存しない系統を残す」も満たせる。Web カメラ単体では距離が測れない（検出枠の大きさからの目安しか出ない）ので、1 m の判定には使わない。
   - G1 の LiDAR（Livox MID360）の点群トピック `rt/utlidar/cloud_livox_mid360`（PointCloud2）は、リポジトリの調査に記録がある ✅（`G1_NAVIGATION_READONLY.md`）。ただし次の点は未解決。
     - **2026-09-12 の調査では、LiDAR の実データが受信できなかった**（総合 FAIL。`G1_NAVIGATION_READONLY_2026-09-12.md`）。それ以前の調査では受信できている。つまり安定して取れるかは❓。
     - 点座標の精度と、LiDAR から G1 の胴体座標への校正は**未検証**（同上）。
     - 点群は「人」と「壁・机・Pepper」を区別しない。1 m 以内に何か入ると止まる設計になるので、現場の壁や物の近くでは誤停止する。除外の方法（既知の物を除く・高さで絞る）は❓。
     - MID360 は水平 360° を見られるはずだが、これは一般仕様で、リポジトリでは確認していない❓。確認できれば、背後の死角も解消する。
   - 実機で、LiDAR の点群を 1 m 判定に使えるかを先に試験する（G-07 を実装する前の段階 0）。
3. 緊急停止のとき、ゲームを GAME OVER にするか → **決定（する）**。
4. 「再開」の意味（要件書 §6 の 1）。本書の仮定: 再開 = ラッチ解除してゲーム状態を「準備」に戻す（G1 はその場で停止のまま）。そのあと「リセット」で G1 が初期位置へ戻る。
5. 実機で確かめること: 戻り量の誤差／指令の期限切れで G1 が止まるか／`GetFsmId` の「歩行可能」の値／Pepper の頭の動作中断 API／バッテリーの読み方。
6. しきい値（仮）はすべて実測で決める: 時間切れ 2 秒、鮮度 5 秒、映像の遅れ 0.5 秒、停止の再送 3 回・0.2 秒間隔。

## 6. スクリプトに分けるときの目安

- チェックは 1 つ 1 関数（`check_g03_lowstate_fresh()` のように ID を名前に入れる）。戻り値は §1.1 の型。
- ボタンごとに「チェックの ID の並び」と「実行手順」を持つ薄いハンドラにする（`on_patrol_start`、`on_patrol_stop`、`on_reset`）。
- ロボット操作は G1 と Pepper を分けた小さなアダプタ（接続・速度指令・停止・状態取得）に閉じ込める。後から Sim やモックに差し替えられるようにし、**テストはモックで書く**（既存の `test_naoqi.py` のように呼び出しを記録するフェイク ✅）。
- 実機の送信は、既存方針どおり**明示的なゲート**（ロボットの種類・許可フラグ）を通ったときだけ行う。

## 7. 付録: G1 へ指示を届ける方法の選択肢（§5 の 1）

前提（既存の方針 ✅）: G1 の歩行指令（`LocoClient`）は PC2 の中でしか送れない。ダッシュボードは運営の PC（または別のサーバー）で動く。つまり**ダッシュボードのボタンは、そのままでは G1 に届かない。**

| 案 | 内容 | 良い点 | 気になる点 |
|---|---|---|---|
| A | PC2 に小さな受け口プログラム（「巡回開始」「停止」を受けて、PC2 の中で `LocoClient` を呼ぶ）を置く | 構成が素直。状態（lowstate・LiDAR）もここから返せる | 「PC2 に新しいスクリプトを置かない」という既存方針の変更が要る |
| B | 運営 PC から SSH を 1 本つなぎっぱなしにし、標準入力で PC2 のプログラムを流し込んで動かす（ファイルは置かない） | 既存方針（PC2 に何も置かない）のまま。SSH が切れればプログラムも終わり、短い速度指令の期限切れで G1 が止まる想定（実機未検証❓） | 常時つなぎっぱなしの運用。停止指示をどう流すかの作り込みが要る |
| C | 運営 PC を G1 の内部ネットワーク（192.168.123.x）に有線でつなぎ、PC から直接 DDS で動かす | PC2 に何も置かない | 既存の安全ゲート（PC2 以外では動かさない）を外す変更になる。Wi-Fi の LAN とは別に有線が要る |

| D | **ダッシュボード自体を PC2 で動かす**（2026-11-07 ユーザー提案）。運営 PC とスマホは、ブラウザで PC2 を開く | 指令・lowstate・LiDAR がすべて PC2 の中に閉じる。**1 m の安全停止（LiDAR → `StopMove`）をネットワークに頼らず PC2 の中で完結できる**。中継が要らない | 下記の 4 点が未確認。方針変更（PC2 にコードを置く）は A と同じ |

D の未確認点（実機で確かめる）:

1. **PC2 の余力**。PC2 は G1 本体の処理（歩行・LiDAR ドライバなど）も動かしている。ここに Web サーバーを足して G1 の動作が不安定にならないか。既存の PC2 用ランタイムは Python 3.8 の専用 venv ✅ なので、使えるライブラリにも制約がある。
2. **YOLO を PC2 で動かせるか**。ユーザーの見立て（2026-11-07）では「YOLO 程度なら PC2 でも動く可能性がある」。**未測定**なので、実機で測る。動くなら、G1 の Web カメラの映像が PC2 の中で済み（映像を送らなくてよい）、検知・距離・停止がすべて PC2 で完結する。測る項目: 小さいモデル（例: YOLOv8n 級）の処理速度（**0.2 秒の連続検知を判定するには、最低でも 1 秒に 10 枚程度は欲しい**。0.2 秒に 2 枚以上入る計算）、CPU/GPU の使用率、そのときの歩行・LiDAR ドライバへの影響（lowstate の遅れ）。足りなければ YOLO だけ別の PC に出す。Pepper の映像は、PC2 から Pepper（NAOqi 9559）へ届くかも確認する。
3. **運営 PC とスマホから PC2 に届くか**。Desktop は SSH で PC2 に届いているが、内部 .164 への Wi-Fi 経路は仮定しない方針 ✅。スマホが同じ Wi-Fi から PC2 の画面を開けるかは❓。
4. **ダッシュボードが落ちても安全側にする**。UI と、1 m 停止・通信断停止（安全側の処理）は**別プロセス**にする（safety.md の「ゲームの判定と安全停止は別系統」）。

**回答（2026-11-07）**: PC2 にコードを置いてよい（y）／運営 PC・スマホから PC2 に Wi-Fi で届く（y）／PC2 が Web サーバーを足しても安定して動くか（**不明**）。
→ **D（PC2 に置く）で進める。**不明の 3 点目は、実装前に実機で測る（段階 0）。測って不安定なら、PC2 に置くものをさらに絞る（安全停止と G1 制御だけ）か、案 B に戻す。

私の推奨は **D の「薄い形」**: PC2 には (a) G1 の制御、(b) LiDAR による 1 m 停止、(c) 状態の配信だけを置く小さなサーバーを載せる。ダッシュボードの画面やゲームの状態機械、Pepper の制御は PC2 の外に置くか、PC2 に載せても軽いものだけにする。YOLO は、上の測定で PC2 に余力があれば PC2 に載せてよい。これは A に近いが、「PC2 に置くのは安全に関わる最小限」と線を引ける点で、ユーザー提案の利点（安全停止がローカルで完結する）を最大限に活かせる。B は、PC2 に何も置けない場合の代替案とする。決めるのはチームの方針なので、PC2 にコードを置いてよいか、先に確認が要る。

> 要確認: `G1_LOCAL_ENV.md` では Desktop の有線が 192.168.123.99 だが、Pepper の有線 IP も 192.168.123.99 と記録されている（Pepper 側の記録は別文書）。同じ IP が両方にあるなら衝突する。現場の IP の割り当てを確かめる。
