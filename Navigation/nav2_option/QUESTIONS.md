## Q9. Nav2 を動かす ROS ディストリをどれに確定するか（2026-09-13）

**背景**: A-10c の実測で「PC2 ネイティブの Foxy には `nav2_velocity_smoother` と
`nav2_behaviors` が存在しない」ことが判明した。自作 3 パッケージ自体は Foxy / Humble
どちらでも無修正で動くので、**制約は Nav2 本体の側にある。**

| 選択肢 | メリット | デメリット |
|---|---|---|
| **(a) Humble コンテナで動かす**（暫定でこれを前提に進めている） | Mapping 用に**既にある**イメージを使い回せる。A-10b・A-10c の検証も全て Humble で通っている。今すぐ進める | D-01（Jazzy 継続）と食い違う。`enable_stamped_cmd_vel` が使えないなど Jazzy 前提の記述を都度読み替える必要がある |
| (b) Jazzy コンテナを新規に作る | D-01 と一致。`g1_ws` が本来想定している環境。Kilted 以降への移行も楽 | イメージを一から作る手間。FAST-LIO の Jazzy ビルドは検証済み（A-6）だが、Nav2 一式＋arm64 での動作は未検証。**着手が遅れる** |
| (c) PC2 ネイティブの Foxy に Nav2 を自前ビルド | コンテナ不要で最も軽い | `velocity_smoother` / `behaviors` を Foxy へバックポートする作業が必要。**現実的でない** |

**暫定の判断**: **(a)** で進めている。理由は、A-10b / A-10c の検証資産がすべて Humble
上にあり、ここで環境を変えると検証をやり直すことになるため。
`g1_cmd_router` は両方の型を購読するようにしたので、後から (b) に移っても配線は壊れない。

**確認したいこと**: (a) のまま進めてよいか、それとも D-01 に合わせて (b) にするか。

## Q10. 「NAVIGATING なのに指令が来ない」ときに FAULT へ落とすべきか（2026-09-13）

**背景**: SafetyManager は「最初の指令を受け取るまで `cmd_timeout` の計測を始めない」
設計になっている（Nav2 の計画時間を待つため、2026-09-09 に意図して入れた猶予）。
ところが A-10c で配線ミス（型の食い違い）を踏んだとき、**この猶予が無期限の沈黙**に
なり、エラーも FAULT も出ないままロボットが動かないだけ、という状態になった。

| 選択肢 | メリット | デメリット |
|---|---|---|
| **(a) WARN を出すだけ（今回入れたのはこれ）** | 安全状態機械の意味論を変えない。Nav2 の計画が長引いても誤 FAULT しない | 無人運用ではログを誰も見ない。物理的な安全は SDK 側 watchdog 頼み |
| (b) 猶予に上限を設け、超えたら FAULT | 配線ミス・上位の停止が確実に FAULT として表面化する。ゼロ速度が送られる | 上限を短く取りすぎると Nav2 の計画中に誤 FAULT する。上限値を決める根拠が要る（実測では計画に約1秒） |
| (c) FAULT にはせず READY へ戻す | 誤 FAULT のリスクなく NAVIGATING から抜けられる | 「異常だった」痕跡が残らない。上位が再度 enable すれば同じことが起きる |

**暫定の判断**: **(a)**。安全に関わる状態遷移を独断で変えたくないため、
今回は可視化にとどめた（`no_cmd_warn_s`、既定 3.0 秒。0 で無効）。

**確認したいこと**: (b) にするか。するなら上限は何秒が妥当か
（Nav2 の計画時間の実測は約1秒。5〜10秒なら誤 FAULT はまず起きないと考えられる）。

## Q11. D-23（TwistStamped で標準化）の扱い（2026-09-13）

D-23 は「`enable_stamped_cmd_vel = true` とし TwistStamped を標準化する」としていたが、
**Humble にはこのパラメータ自体が無く、標準化は成立しない**ことが分かった。

現状は `g1_cmd_router` が両方の型を購読することで回避している。
D-23 の記述は「両方受ける」に**書き換え済み**（Planning.md §1.3）。

**確認したいこと**: この書き換えでよいか。
なお D-23 が挙げていた「タイムスタンプで stale な指令を弾く」という利点は、
`Twist` で受けている間は使えない（現状 stale 判定は `cmd_timeout` の経過時間のみ）。
これを重視するなら Q9 の (b)=Jazzy を選ぶ理由になる。

## Q12. 操作PC との通信が切れたとき、巡回を止めるべきか（2026-09-13）

**背景**: 2026-09-09 の実測で、走行中に `g1-link` を切っても**ロボットは 4.045 秒
歩き続け、約 0.85m 前進した**。既存の3層の watchdog は**すべて「オンボード側の誰かが
死ぬこと」を検知する仕組み**で、通信断ではオンボード側は全員無事なので誰も気づかない。
Nav2 を載せると `bt_navigator` が Goal を完走しようとするのでさらに悪化する。

対策として操作PC の生存監視（heartbeat）を設計した
（[findings/operator_heartbeat_design.md](findings/operator_heartbeat_design.md)）。
技術的な設計はできたが、**方針の選択が残っている。**

| 方針 | メリット | デメリット |
|---|---|---|
| **(a) 止める**（設計案の前提） | 人が見ていない状態でロボットが動き続けない。通信断＝監視不能なので、事故が起きても誰も気づけない | 自律巡回の意味が薄れる。Wi-Fi の弱い場所で巡回が中断し続ける可能性 |
| (b) 止めない（ログのみ） | 電波の届かない区画も巡回できる | **実測で証明された穴がそのまま残る。** 遠隔から止める手段が無い |
| (c) 減速して継続 | 妥協案 | 📌 **U-12 により実質選べない。** `vx=0.2` で進行方向が定まらなくなるため、「ゆっくり歩いて帰る」が物理的に存在しない |

**暫定の推奨**: **(a)**。警備 PoC の目的が「異常を見つけて人に知らせること」である以上、
人と繋がっていない状態で動き続けることに価値が無いため。

**確認したいこと**:
1. (a) でよいか
2. よければ `operator_timeout_s` の初期値（案は 1.0 秒。短すぎると Wi-Fi の
   瞬断で巡回が止まる。会場 room_a の電波状況次第なので実機で詰めたい）
3. 途絶時の遷移先は `FAULT` でよいか（`E_STOP` は手動解除必須なので、
   瞬断のたびに現地へ行く必要が出る。`FAULT` なら `/g1/clear_fault` で遠隔復帰できる。
   ただし**自動復帰はさせない** — 人が明示的に叩く）
