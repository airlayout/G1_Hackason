# pointcloud_to_occupancy_grid

Planning.md A-7 に対応。点群地図(`.pcd`/`.ply`)から Nav2 `map_server` 形式(`.pgm`+`.yaml`)への
変換ツール。

## セットアップ

必須は `numpy` のみ。`scipy` は連結性の計測に使う(無くても変換自体は動く)。
`.pcd` は内蔵リーダーで読めるので **open3d は任意**(`.ply` 等を読むときだけ必要)。

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install numpy scipy      # open3d は .ply を読む場合のみ追加
```

## 使い方

```bash
# 推奨: 軌跡を渡してレイトレーシングまで行う
python3 pointcloud_to_occupancy_grid.py map_20260907.pcd \
    --trajectory <mapping実行の>/trajectory/trajectory.tum \
    --bounds -5.5 23 -17.5 15.5 --resolution 0.05 --out room_a_map
```

生成される `<out>.pgm` / `<out>.yaml` はそのまま Nav2 の `map_server` に渡せる。

### 主なオプション

| オプション | 既定値 | 意味 |
|---|---|---|
| `--resolution` | 0.05 | グリッド解像度[m/cell]。`nav2_params.yaml` の global_costmap と揃える |
| `--min-height` / `--max-height` | 0.3 / 1.8 | 障害物とみなす高さ範囲[m]。**床からの相対高さ**(D-21) |
| `--floor-z` | 自動検出 | 床の絶対Z[m]を明示指定する |
| `--bounds` | 点群全体 | 地図範囲 X_MIN X_MAX Y_MIN Y_MAX。外れ値で地図が巨大化するのを防ぐ |
| `--trajectory` | なし | mapping 実行時の軌跡(TUM形式)。レイトレーシングと軌跡カーブに使う |
| `--max-range` | 15.0 | レイトレーシングの最大距離[m] |
| `--rays` | 720 | 1姿勢あたりの光線本数 |
| `--carve-radius` | 0.25 | 軌跡に沿って占有を削る半径[m](G1の機体半径) |
| `--no-carve` | off | 軌跡カーブを行わない(生の判定結果を見たいとき) |
| `--occupied-min-points` | 1 | 高さ帯内の点がこの数以上あるセルだけを占有とみなす |
| `--padding` | 1.0 | `--bounds` 省略時に点群の外周へ足す余白[m] |

## 設計上のポイント

### 1. 未観測を「自由」にしない(3値で出力する)

高さフィルタ範囲外の点しか無いセルを一律「自由」と判定すると、実際には未観測なだけの
領域が「自由に通れる」と誤判定され、Nav2 の経路計画が建物の外側や壁の裏を通ろうとする
問題が起きる(姉妹プロジェクト `Navigation/` の知見を踏襲)。そのため 3 値で出力する:

- **occupied(黒, 0)**: 高さフィルタ範囲内に点があるセル
- **free(白, 254)**: 観測済み・レイトレーシングで可視・ロボットが通った、のいずれかで障害物でないセル
- **unknown(灰, 205)**: 上のどれにも当たらないセル(未観測)

### 2. 高さは「床からの相対高さ」で判定する(2026-09-09 修正)

**旧版は絶対 Z 座標にフィルタをかけていた**(床が Z≒0 にある前提)。実機データでは
成り立たない。`map_20260907.pcd`(room_a セッション)の実測:

```
床   : 絶対 Z ≈ -1.26m (全体の 34%)
天井 : 絶対 Z ≈ +1.50m (全体の 約18%)
```

この状態で旧既定値(絶対 Z の 0.3〜1.8m)を使うと実際には「床上 1.55〜3.05m」＝天井付近を
見ることになり、机・椅子を拾えず天井を障害物として誤検出する。`find_floor()` が
Z ヒストグラムの下半分の最頻ビンから床を検出し、相対高さで判定するようにした
(姉妹実装 `Navigation/nav3/pcd_to_ros_map.py` が同じバグを踏んで修正済みで、それに合わせた)。

### 3. 自由空間はレイトレーシングで繋ぐ(2026-09-09 追加)

**旧版は「点があるセル」だけを free にしていた。** 床面の観測は疎なので、これだけでは
自由空間が分断されうる。`--trajectory` を渡すと各姿勢をセンサー原点として 2D の光線を
飛ばし、最初の occupied に当たるまでのセルを free にする。

制約: 壁のセルが観測漏れで欠けていると光線が室外へ漏れる。`--max-range` を実際の
センサー到達距離程度に抑えて影響を限定する(OctoMap の `sensor_model.max_range` と同じ考え方)。

### 4. 軌跡に沿った偽の障害物を削る(2026-09-09 追加)

**ロボットの機体がそこに在ったこと自体が、そこが通行可能である最強の証拠**である。
それでも occupied と判定される場合、地図側に偽の障害物が残っている:

- 追従者(PC を持った人物)がロボットの直後を歩き、その胴体が経路上に焼き付いている
  (`Navigation/nav3/README.md` が「閾値を上げても消えない斜めの筋」として報告した動的物体の残り)
- 至近距離では機体自身が頭部 LiDAR に写る(`Navigation/nav2/g1_nav2.yaml` の
  `obstacle_min_range: 0.30` も同じ理由)

`--carve-radius`(既定 0.25m = 機体半径)で軌跡に沿って占有を削る。**軌跡がドリフトして
いると本物の障害物を削る危険があるため、機体半径以上に広げないこと。**

## 動作確認(2026-09-09、G1実機データ)

`map_20260907.pcd`(room_a セッションの SLAM 出力、544,760点)と同セッションの
`trajectory.tum`(3,113姿勢)で検証した。

```
[grid] 570 x 660 セル (0.05 m/cell) / 範囲 x[-5.50,23.00] y[-17.50,15.50]
[grid] 範囲内の点: 537126/544760
[grid] 床 Z(絶対座標)=-1.264m と推定
[grid] 軌跡に沿って占有を削った: 88 セル (機体半径 0.25m 相当)
[grid] レイトレーシング: 720方向 / 最大 15.0m / free セルを 22842 増やした
[info] occupied=41126 (10.9%) free=182817 (48.6%) unknown=152257 (40.5%)
[conn] free の連結成分: 7221 個 / 最大 158877 セル (397.2 m², free 全体の 86.9%)
[conn] 軌跡 3113 姿勢中: 最大連結成分の上 3113 (100.0%) / occupied の上 0 (0.0%)
```

生成物: `../../g1_ws/src/g1_navigation/maps/room_a_map.{pgm,yaml}`

**独立実装との一致による裏付け**: 同じ入力・同じ `--bounds` で
`Navigation/nav3/pcd_to_ros_map.py`(別実装)が報告した「範囲内の点 537,126/544,760」と
完全に一致し、占有率も同等(あちらは解像度0.1で自由52.0%/占有12.2%/未知35.8%)。
独立した2実装が同じ結果に到達している。

**軌跡カーブの効果(実測)**: `--no-carve` だと軌跡 3,113 姿勢のうち **476 姿勢(15.3%)が
occupied セルに乗る**。Nav2 の planner は開始点が障害物内だと計画自体を拒否するため
(`Navigation/nav3/README.md` が MuJoCo 検証で踏んだ失敗)、この状態では実質使えない。
カーブ有効時は 0 件になる。

## Nav2 で実際に経路が引けることを確認済み(2026-09-09)

`map_server` → `global_costmap`(static_layer) → `planner_server`(NavfnPlanner) を
Humble のコンテナで動かし、`ComputePathToPose` を投げて確認した。
始点・終点は軌跡の両端(＝ロボットが実際に居た点)を使った。

```
[global_costmap] StaticLayer: Resizing costmap to 570 X 660 at 0.050000 m/pix
[OK] 経路が引けた: 967 点 / 経路長 24.18 m (直線距離 19.88 m, 迂回率 1.22)
```

`allow_unknown: false`(未観測を通らせない)・`inflation_radius: 0.55` の条件でも
経路が引けている。表示手順は [../view_map_rviz.sh](../view_map_rviz.sh) を参照。

## 未検証・既知の制約

- **controller(経路追従)側の検証はまだ**。上記は planner までで、実際に歩かせる検証は
  Phase 1 以降(実機)と Phase 2c で行う
- 上記の planner 検証は **Humble** の Nav2(1.1.20)で行った。nav2_option 本体の
  `g1_ws` は **Jazzy** 向け(D-01)なので、`nav2_params.yaml` そのままでの疎通は別途確認が必要
- 高さフィルタの既定値(床上 0.3〜1.8m)は D-21 の値を踏襲したもの。低い障害物(床上 0.3m 未満)は
  意図的に落としており、Local costmap の 3D 点群側で見る前提(D-21)。
  なお `Navigation/nav3` は同じデータに対し実測で床上 0.10〜1.50m を採っている
- レイトレーシングのセンサー原点は軌跡の XY のみを使い、高さ・姿勢は考慮していない
  (2D 地図なので影響は無いが、傾斜のある環境では見直しが必要)
- 大きい孤立した未観測領域の扱いは Nav2 の `unknown_cost_value` 側で調整する想定
  (`--fill-interior-unknown` で内部の死角を自由に倒すことも可能)
