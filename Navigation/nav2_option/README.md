## 1. 登場人物

機械が3つあります。**どれが何をしているか**を押さえると、あとが楽になります。

```
 ┌─────────────┐   LAN    ┌──────────────┐  内部    ┌─────────┐
 │  操作PC     │─────────│  PC2         │─────────│ G1 本体 │
 │ (あなたのPC)│ .222/.223│ (Orin NX)    │ .164     │  .161   │
 └─────────────┘          └──────────────┘          └─────────┘
   RViz で見る              **Nav2 が動く**           歩く・LiDAR
   heartbeat を送る         ここが頭脳                 を出す
```

- **操作PC** … 人が見て、人が判断する。⚠️ **ROS は入っていません**
- **PC2** … G1 の背中に載っている小型コンピュータ。**Nav2 はここで動きます**
- **G1 本体** … 脚と LiDAR。「前へ 0.3 m/s」と言われたら歩く

⚠️ **操作PC の IP は `192.168.123.222` が既定**（`nmcli connection up g1-link` で有効化）。
2026-09-25 に**別の機器（ELECOM製）が .222 を使っていて衝突**し、`.223` へ変更した。
症状は「ケーブルは繋がっているのに IP が付かない」。原因は
`journalctl -u NetworkManager` に `IP address ... is already in use` と出る。
変更は `nmcli connection modify g1-link ipv4.addresses 192.168.123.223/24`。
📌 **操作PC の IP はどこにも埋め込まれていない**ので、変えても他に影響しない
（CycloneDDS は PC2 側の `eth0` に束縛、heartbeat の宛先は PC2 の `.164`）。

📌 **なぜ分かれているか**: G1 本体の ROS は古い版（Foxy）で Nav2 が動きません。
PC2 に新しい版（Humble）を `pixi` という仕組みで入れて、そこで Nav2 を回しています。

## 2. 自分がどこに居るか（いちばん大事な話）

ロボットは「自分が地図のどこに居るか」を、**3つの座標系をつないで**表します。

```
map ──────→ odom ──────→ base_link
 ①            ②
```

| | 意味 | 誰が出すか |
|---|---|---|
| `map` | **部屋に固定された座標**。地図の左下が原点 | 動かない |
| `odom` | **出発点に固定された座標** | 内蔵SLAM |
| `base_link` | **機体そのもの** | — |

**②「odom → base_link」＝ 出発点からどれだけ動いたか。**
G1 の内蔵SLAM（LiDAR で自分の動きを測る機能）が出します。
⚠️ **車輪の回転数ではありません。**歩行機には車輪が無いので、景色の動きから割り出しています。

**①「map → odom」＝ 出発点が地図のどこだったか。**
⚠️⚠️ **これは起動時に1回決めて、あとは固定です。** 走行中は誰も直しません。

### だから何が起きるか

②が少しずつ狂う（＝**ドリフト**）と、①が固定なので、**狂った分そのまま地図上の位置がずれます。**
**直す仕組みが入っていません。** 実測では直進5mで7cmですが、
**その場でぐるぐる回ると一気に壊れます**（2026-09-25 に最終的に10.8mずれた）。

📌 **Nav2 には「ずれている」と気づく手段がありません。**
地図と実際が合っているか確認するのは、**起動時の1回（§7）と、人の目視だけ**です。

## 3. 障害物をどう避けているか

**Nav2 が全部やっています。内蔵SLAM は関係ありません**（内蔵SLAMは②を出すだけ）。

Nav2 は「**costmap**」という格子の地図を**2枚**持ちます。1マスごとに
「そこに居ることの悪さ」の数値が入っています。

| | global costmap | local costmap |
|---|---|---|
| 何のため | **経路を引く** | **いま進んでよいか判断する** |
| 範囲 | 部屋全体 | **機体の周り 6×6m だけ**（機体について回る） |
| 入力 | **保存した地図（.pgm）だけ** | **LiDAR の点群だけ** |

⚠️⚠️ **ここが最大の落とし穴です。**

- 経路を引く側（global）は **LiDAR を見ていません**。保存地図しか知りません
- 目の前の人を見ている側（local）は **経路を引けません**

**結果: 地図に載っていない障害物（人・動いた椅子）を迂回できません。**
planner は人が立っている場所を通る経路を引き続け、controller は
「ぶつかる」と言って進まず、**同じ場所で止まり続けます。**

これは既知の制約で、[nav2_params.yaml](g1_ws/src/g1_navigation/config/nav2_params.yaml)
の `global_costmap` のところに理由が書いてあります。

## 4. 「進め」がどう伝わるか

```
planner_server ──/plan──→ controller_server ──/cmd_vel_nav──→ velocity_smoother
                          (経路を追いながら                          │
                           local costmap で衝突を見る)      /cmd_vel_smoothed
                                                                    ↓
                                                            g1_cmd_router  ← **安全の番人**
                                                                    ↓ Unix ソケット
                                                        g1_sdk_bridge_real_server
                                                                    ↓
                                            LocoClient::SetVelocity(vx, vy, wz)
```

指令は「前へ 0.3 m/s、右へ 0.2 rad/s」という**速度**です。
関節をひとつずつ動かしているわけではありません。

## 5. 安全の仕組み（3重になっています）

### ① 発進ゲート（`G1_ARM`）

`/etc/default/g1-sdk-bridge` の1行です。

```
G1_ARM=        ← 閉。**何をしても機体は動かない**
G1_ARM=--arm   ← 開
```

⚠️ **ここを開けるのは必ず人の手で、sudo パスワードを入れて行います。**
意図的に自動化していません（「再起動したら勝手に動けるようになっていた」を防ぐため）。

### ② 走行許可（`enable_navigation`）

ゲートが開いていても、これを出すまで動きません。`READY` → `NAVIGATING` に変わります。

### ③ `g1_cmd_router` — 6つの見張り

異常を見つけたら **FAULT** にして、Goal ごと捨てて止めます。

| 見張り | 意味 |
|---|---|
| `cmd_timeout` | Nav2 からの指令が途切れた |
| `tf_stale` | **自分の位置が分からなくなった**（内蔵SLAMが止まった等） |
| `sensor_stale` | LiDAR が来ない |
| `operator_lost` | **操作PCとの通信が切れた**（死人スイッチ） |
| `sdk_bridge_error` | SDK側と繋がらない |
| `e_stop` | 緊急停止 |

📌 **FAULT は自動では戻りません。**原因を潰して `clear_fault` を叩き、
巡回を `start` し直す必要があります。

⚠️ **`operator_lost` は実際によく起きます。**LANケーブルが抜けた／
NetworkManager が接続を落とした、で即停止します。これは**正しい動作**です。

## 6. 当日の流れ

**③ではじめて歩きます。①②では動きません。**

| 段 | やること | 機体 |
|---|---|---|
| 準備 | 機体を**通常の立位**で出発位置へ。人は2m以上離れる | 立つだけ |
| §2〜§7 | `~/g1_nav2/g1up.sh` を叩く（全部自動） | 動かない |
| **目視** | **RViz で位置と向きを確認する** ← **省かない** | 動かない |
| ① | 発進ゲートを開く（sudo） | まだ動かない |
| ② | `g1up.sh --enable` | まだ動かない |
| ③ | `tools/patrol_ctl.sh start` | **ここで歩き出す** |

`g1up.sh` が中でやっていること:

```
§1 機体の姿勢を検査（立っているか）
§2 SDK側プロセスを起動（ゲートは閉じたまま）
§3 内蔵SLAM を開始（API 1801 を送る）
§4 記録を開始（rosbag）
§5 Nav2 を起動
§7 **地図と実際を照合して map→odom を決める**  ← 2章の①
```

## 7. 初心者がはまる点（全部、実際に踏んだものです）

### ⚠️ RViz の目視確認を飛ばさない

§7 の照合は「一致率」を出します。**80%未満なら警告が出ます。**
2026-09-25 に **47%** のまま走らせ、機体が見当違いの場所へ歩きました。

⚠️⚠️ **「何回やっても同じ値が出た」は、正しさの証拠になりません。**
照合が安定して**誤った場所**を指すことがあります。**人の目だけが最後の砦です。**

### ⚠️ 内蔵SLAM は20〜26分で勝手に止まる

止まると TF が途切れ、`tf_stale` で FAULT になります。原因は不明です。
止まったら **1801 を送り直し → §7 をやり直し**（odom の原点がリセットされるため）。

```bash
cd ~/g1_nav2/tools && /usr/bin/python3 send_slam_api.py 1801
```

⚠️ **`/usr/bin/python3` で叩くこと。** pixi の Python には必要な部品が入っていません。

### ⚠️ 「障害物」は本物とは限らない

local costmap は**記憶**です。一度「障害物」と書かれたマスは、そこを
**LiDAR の光線が通り抜けるまで消えません**。
⚠️ **LiDAR は自分の周り約1mを見られない（死角）**ので、
**死角に入った印は永久に残ります。**

歩くほど足元に幻の障害物が溜まり、やがて `collision ahead` で止まります。
実測: costmap を消すと 33セル→0セル、**静止14秒では戻らず**、
**約100秒歩くと37セルに再蓄積**。詳細は
[findings/collision_ahead_cause_20260925.md](findings/collision_ahead_cause_20260925.md)。

暫定処置として、走行中に定期的に costmap を消しています。
⚠️ **本物の障害物も一瞬消える**ので、**人が見ている場でしか使えません。**

### ⚠️ ゴールに着いても止まれないことがある

Nav2 は「**位置と向きを同時に**満たす」ことを到達条件にします。
歩行機は**その場で回ると位置がずれる**ので、回れば位置が外れ、
位置を直せば向きが外れ、**永久に回り続けます**（2026-09-25 に180秒間発生）。
判定を緩めて対処しました（`yaw_goal_tolerance: 1.00`）。⚠️ **実機で未検証です。**

### ⚠️ `/tmp` のログは再起動で消える

`/tmp/nav_launch.log` は PC2 を再起動すると失われます（実際に失いました）。
記録（rosbag）には `/rosout` が入っているので、
[tools/bag_read_rosout.py](tools/bag_read_rosout.py) で復元できます。

### ⚠️ 記録には点群を含める

既定の `diag` プロファイルには**点群が入っていません**。
入れておかないと、**「何が障害物として書き込まれたのか」を後から調べられません。**

### ⚠️ PC2 へ配るときは `maps/` と `g1_sdk_bridge_cpp/` も送る

`g1_ws/src/` だけ送るとビルドが落ちます。手順は [HANDOVER.md](HANDOVER.md) に。

## 8. 困ったときに叩くもの

```bash
# いまどういう状態か
ros2 topic echo --once /g1/bridge_status        # READY / NAVIGATING / FAULT と理由
~/g1_nav2/tools/patrol_ctl.sh status            # 巡回の状態

# 足元から出発できるか（経路が出ないとき）
python3 ~/g1_nav2/tools/can_start_here.py

# costmap に何が写っているか
python3 ~/g1_nav2/tools/count_costmap.py        # footprint 内に障害物があるか
python3 ~/g1_nav2/tools/why_costmap.py          # 一様なリング(水平の狂い)か、偏り(人や物)か

# 止める
~/g1_nav2/tools/patrol_ctl.sh pause
```

⚠️ **緊急時は純正リモコン**です。ソフトウェアを信用しないこと。

📌 **ROS のコマンドは、PC2 で pixi の環境を通してから叩きます。**
素の端末では `ros2: command not found` になります。手順は runbook に。
