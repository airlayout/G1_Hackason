# 失敗ログ（nav2_option）

`Navigation/FAILURES.md` と同じ形式。このフォルダでの開発中に実際に起きた失敗と、
その原因・反省・再発防止策を記録する。

## テンプレート

```
## YYYY-MM-DD: 失敗の一言タイトル

**何が起きたか**
（観測された事実。憶測ではなく実際に見えたことを書く）

**原因**
（コード上・手順上の根本原因）

**反省**
（なぜ事前に気づけなかったか。見落としていた前提は何か）

**再発防止策**
（実際にコード/手順をどう変えたか）
```

## 2026-09-08: `on_nav_twist()` の初回呼び出しが常にゼロを返すバグを、テストが検出できていなかった

**何が起きたか**

`SafetyManager.on_nav_twist()` に、NAVIGATING に遷移してから最初に呼ばれたとき、
指令の内容に関係なく必ず `(0.0, 0.0, 0.0)` を返すバグがあった。原因は
`self._last_tick_time` が `enable_navigation()` 時点で初期化されておらず、
`on_nav_twist()` 内で `dt = 0.0 if self._last_tick_time is None else ...` という
条件分岐により、初回は `dt=0` 扱いになって `accel_limit` を呼ばずに
`self._last_output`（初期値ゼロ）をそのまま返していたため。

これを検証するはずだった `test_nav_twist_is_clamped_and_forwarded_while_navigating` は、
`self.assertLessEqual(abs(out[0]), limits.max_vx + 1e-9)` という緩い assertion だった。
バグにより `out[0]` が常に `0.0` になっていたが、`0.0 <= 0.2` は真なので**テストは緑のまま
通り続けていた**。

**原因**

「上限を超えないこと」だけを検証する assertion にしていた。バグの結果（常にゼロ）も
「上限を超えない」という条件を満たしてしまうため、テストがバグを覆い隠す形になっていた。

**反省**

`accel_limit` の単体テスト（`TestPureFilters`）は正しく書けていたので、関数自体の
ロジックは検証できていた。しかし `SafetyManager` 側の**呼び出し方**（`dt` の計算・
初期化タイミング）は状態機械のテストでしか検証できず、そこの assertion が緩かった。
「動くはず」を確認するテストではなく「期待する具体的な値」を確認するテストで
なければ、この種のバグは検出できない。

**再発防止策**

- `enable_navigation(True)` の中で `_last_tick_time` と `_last_output` を明示的に
  初期化するよう修正した。これにより「NAVIGATING に入った瞬間からの経過時間」で
  `accel_limit` が常に一貫して動くようになり、`on_nav_twist()` 側の特別扱い
  （`if dt > 0 else self._last_output`）を削除できた
- 該当テストの assertion を `assertLessEqual`（範囲チェック）から
  `assertEqual(out, (limits.max_vx, 0.0, 0.0))`（具体的な期待値）に変更した
- 新たに `test_nav_twist_ramps_up_gradually_right_after_enable` を追加し、
  「enable 直後は急加速せず、徐々に増える」ことを2回の呼び出しの比較で検証するようにした
- 教訓: 状態を持つオブジェクトのテストでは、「範囲に収まっている」ではなく
  「この値になるはず」を assert する。特に初期値がたまたま安全側（ゼロ）の値だと、
  ロジックが機能していなくてもテストが通ってしまう

## 2026-09-09: Nav2をNav2フルスタックで動かして初めて見つかった2件の不具合

**何が起きたか**

`g1_navigation`（Nav2設定+疑似データでの動作確認）を実装し、実際にNav2の
`controller_server`/`bt_navigator`等をすべて起動してGoalを送ったところ、ロボット
（SDK側モックの簡易積分）が一切動かず`odom`の位置が(0,0,0)のまま変化しなかった。

デバッグの結果、2つの独立した不具合が重なっていたことが分かった。

1. `EnableNavigation(true)`直後にcmd_timeoutのカウントが始まるため、Nav2のGoal計画
   （実測で約1秒かかる）の間に最初の指令が届かず、`g1_cmd_router`がFAULTへ先に
   遷移していた
2. 1を直しても、`min_wz`のデッドバンド(0.03)がNav2のrotate-to-heading起動フェーズの
   微小角速度(0.02 rad/s)を常時ゼロへ切り捨て、ロボットが永久に動き出せなかった
   （`ros2 topic hz`で`/cmd_vel_smoothed`が20Hzで正常に流れていることは確認できたのに、
   SDK側モックに届く速度は常にゼロだった）

**原因**

1は「有効化した瞬間から安全にゼロ速度を送るべき」という設計が、「有効化してから
実際に動かすまでの正当な準備時間」を考慮していなかったため。
2はD-14のデッドバンドが「Goal到達直前の残留速度対策」と「起動直後の加減速ランプアップ」
という**2つの異なる状況を同じ閾値で扱っていた**ため。前者は微小速度を消したいが、
後者は消してはいけない。

**反省**

どちらも、`g1_sdk_bridge_cpp`/`g1_sdk_bridge`の単体テスト（モックバックエンド、38件）
だけでは検出できなかった。単体テストは「Safety Managerのロジックが仕様通りか」は
検証できるが、「Nav2の実際の出力パターン（Goal計画の所要時間、rotate-to-headingの
実際の角速度値）とSafety Managerの組み合わせが機能するか」は、Nav2を実際に動かして
初めて分かった。個々のコンポーネントが仕様通りでも、組み合わせた時の相互作用は
別問題として検証しないと見つからない。

**再発防止策**

- 1は「最初の指令を受け取るまではcmd_timeoutの判定を待機する」設計に修正し、
  `g1_sdk_bridge_cpp`・`g1_sdk_bridge`双方に回帰テストを追加した
  （`TickDoesNotFaultBeforeFirstTwistEvenAfterTimeoutElapsed`）
- 2は仕様（D-14）そのものに関わる設計判断のため、その場で修正せず
  `nav2_option/QUESTIONS.md` Q8として選択肢を整理し、ユーザー判断を仰ぐことにした
  （デッドバンドの目的が異なる2つの状況を区別する必要があると判明したため、
  安全側の判断を一存で変えなかった）
- 教訓: Safety Managerのようにロジックが仕様書に忠実であることをモックで検証しても、
  それを駆動する実際のシステム（Nav2）の出力パターンとの組み合わせは別途検証が要る。
  「疑似データでの動作確認」を後回しにせず早期にやる価値が、まさにこの2件で実証された

**追記(同日)**: ユーザーがQUESTIONS.md Q8で(d)（Phase 1実測までデッドバンド無効化）を
選択したため反映し、Nav2からのGoal到達を最後まで確認した。その過程で**3件目の不具合**を
発見した: Goal到達直前、Nav2の"Failed to make progress"→再計画のサイクルが`cmd_timeout`
(0.30秒)より長い間隔で発生し、`g1_cmd_router`が再度FAULTへ落ちた。D-13の設計（異常時は
自動復帰しない）どおりに動作した結果だが、Nav2側はそれに気づかず空振りのリトライを
永久に続けていた。手動で`/g1/clear_fault`→`/g1/enable_navigation`を呼び直すことで復帰し、
その後実際にGoalへ到達した（`Reached the goal!` / `Goal succeeded`）。

この3件目は「安全設計としては正しく動作しているが、Nav2の自動リトライと組み合わせると
無限に空振りする」という運用上の課題であり、コードの不具合ではないため未修正のまま
Planning.mdのリスク表に記録した。将来的にはFAULT状態をオペレータへ通知する仕組みか、
`cmd_timeout`とNav2の再計画間隔を実測ベースで整合させる調整が必要になる見込み。
