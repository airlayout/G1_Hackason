# 地図を 2026-09-11 の記録から作り直した（2026-09-16、実機不要）

room_a の地図は 2026-09-07 取得で現状と合っていなかった（A-10n）。作り直せなかった
理由は「**点群はあるが、対応する軌跡が見つからない**」だった。
その軌跡が **9/11 の rosbag の中にあった**。

---

## 1. なぜ軌跡が要るのか

点群は「**物がある場所**」しか教えない。「**何も無い場所**」は分からない。
Nav2 のプランナは**未知セルを通れない**ので、点群だけで作った地図は
「壁が点々とあって周りが全部グレー」＝**経路が1本も引けない地図**になる
（A-7 / A-9 の `test_room.yaml` がこれで失敗した）。

軌跡があると**レイトレーシング**ができる。各姿勢をセンサー原点として光線を飛ばし、
**最初の障害物に当たるまでの経路上を自由空間として彫る**。ロボットが実際に歩いた
場所から見えていた範囲が、連結した自由空間になる。

📌 **要るのは bag ではなく、bag の中の `/unitree/slam_mapping/odom` だけ。**

## 3. 点群は「歩いた範囲」に絞った

点群 `map_wireless_dualcam_01_cleaned_no_ceiling.pcd` は 880 万点で
**x -5.77..51.79 / y -18.87..20.82（57.6m × 39.7m）**あるが、
**99.3% の点は軌跡の bbox から 4m 以内**にある。51.79m まで伸びているのは
0.7% の外れ値だった。

| 軌跡 bbox からの余白 | 含まれる点 |
|---|---|
| 0m | 65.0% |
| 2m | 93.2% |
| **4m** | **99.3%** |
| 8m | 99.9% |

→ `--bounds -5.2 18.6 -19.6 17.8`（bbox + 4m）で生成した。

```bash
python3 tools/pointcloud_to_occupancy_grid/pointcloud_to_occupancy_grid.py \
    Navigation/map_wireless_dualcam_01_cleaned_no_ceiling.pcd \
    --trajectory trajectory/map_wireless_dualcam_01.tum \
    --bounds -5.2 18.6 -19.6 17.8 --resolution 0.05 \
    --out room_a_map_20260911
```

床は絶対 Z = **-1.268m** と自動検出された（9/07 の点群の -1.25m とほぼ同じ）。

## 4. 比較（同じ物差しで測り直した）

⚠️ `pointcloud_to_occupancy_grid.py` は**コンテナに scipy が無いと連結性の計測を
省略する**（「scipy が無いので連結性の計測は省略した」と出るだけ）。
**いちばん大事な指標なので、自前の BFS で測り直した。**

| | **9/07（旧）** | **9/11（新）** |
|---|---|---|
| 大きさ | 28.5 × 33.0 m | **23.8 × 37.5 m** |
| occupied | 102.8 m²（10.9%） | **161.2 m²（18.1%）** |
| free | 457.0 m²（48.6%） | **485.6 m²（54.5%）** |
| **unknown** | **40.5%** | **27.4%** |
| **最大連結の自由空間** | 397.2 m² | **438.7 m²（+10%）** |
| 自由空間の断片 | 7,221 個 | **4,743 個** |

**未知が 13 ポイント減り、連結した自由空間が 10% 増え、断片が 3 割減った。**
Nav2 は未知セルを通れないので、これがそのまま「計画できる範囲」の差になる。

### 重ね合わせ（[map_compare_20260911/](map_compare_20260911/)）

FFT 相関で位置合わせすると **dx=0.00 dy=0.90 yaw=10°** で一致した。

```
yaw= 10.0°  11849 (55%)   ← 最良
yaw=  9.0°  10912         単峰。前後になだらかに落ちる
yaw= 11.0°  10182
yaw=  0.0°   5614 (26%)   ← 恒等の倍以上
中央値       3255          最良/中央値 = 3.64 倍
```

**単峰で中央値の 3.6 倍**なので、この重ね合わせは信用してよい（乱数的なピークなら
飛び飛びの角度に同じような値が立つ）。2枚は**同じ部屋を、約10°違う座標系で記録したもの**。

| | |
|---|---|
| 9/07 の壁のうち 9/11 にもある | **72%** |
| 9/11 の壁のうち 9/07 にもある | **47%** |

この非対称は「**9/11 のほうが細かく拾っている**」という意味（9/07 にある物はだいたい
9/11 にもある。逆は成り立たない）。occupied が 102.8 → 161.2 m² に増えたのと整合する。

⚠️ **この 47%/72% を「会場がどれだけ変わったか」と読んではいけない。**
センサーの密度・視点・ノイズの差が全部混ざっている。

📌 `overlay_aligned.png` を見ると、**外周と机の島は黒（両方一致）**で揃っており、
**青（9/11 だけ）が北側の小部屋群と西側**に広がっている。9/11 のほうが
**歩いて回った範囲が広い**ことが目で見て分かる。

## 5. 25m×25m 制約への影響（良い方向）

| | 範囲 |
|---|---|
| 9/07 の地図 | 28.5 × **33.0** m |
| 9/11 の地図 | **23.8** × 37.5 m |
| **実際に歩いた範囲** | **15.8 × 29.4 m** |

**x は 23.8m で 25m を切った。** 残るのは y だけ。そして**巡回できるのは歩いた範囲だけ**
なので実質 15.8 × 29.4 m。**y を 25m 以内に区切れば、内蔵SLAM の推奨範囲に収まる
巡回路が引ける**（会場全体を1周するのは諦める、という判断にはなる）。

## 6. ⚠️ これで言えないこと（重要）

- **「現状に近いか」は測っていない。今日は原理的に測れない。**
  それを決めるには**実スキャンを両方の地図に照合する**しかなく、機体が要る。
  📌 **2026-09-20、その比較はやらないと決めた（利用者の判断）。**
  構造の比較（未知 40.5%→27.4%、連結した自由空間 +10%）で十分とし、
  新しい地図でそのまま進める。現地の時間は旋回の確認・巡回路の作成・
  16分停止の切り分けに使う。
  ⚠️ **「現状に近いか」を測らないまま進む**ということ。§7 の一致率が
  出発地点で 80% を切ったら、そこで初めて旧地図と比べればよい（退路は残してある）
- **9/11 のスキャンで 9/11 の地図を採点するのは循環**なので意味がない
- **occupied が 1.6 倍になったのは無条件に良いとは言えない。** 本物の什器が出たのか、
  ノイズや**動いている人が焼き付いた**のかは、この数字では区別できない。
  現地で目視確認が要る
- 地図はまだ **9/11 取得**。今日から見れば 5 日前で、**9/07 より新しいというだけ**

## 7. ⚠️ 切り替えに伴って無効になるもの

**2枚の座標系は約10°違う。** したがって**旧地図の座標で書かれたものは全部無効**:

| | |
|---|---|
| `map→odom` の値 | どのみちセッションごとに変わるので §7 で取り直す |
| `start_localizer.sh` の `--initial` | **2026-09-15 の値がハードコードされていた。引数で渡す形に直した**（下記） |
| 巡回路の yaml | まだ作っていないので影響なし。**作るのは切り替え後** |

### 🐛 ついでに見つけた不具合

`g1up.sh` は `start_localizer.sh` を**引数なしで呼んでいた**のに、
直後に `ok "map_localizer を起動した（初期値 $DX $DY $YAWRAD）"` と表示していた。
実際に使われていたのは `start_localizer.sh` 内の**2026-09-15 のハードコード値**で、
**ログが嘘をついていた**。引数で渡すように直し、スクリプト側も引数必須にした。
