# 操作PC 生存監視（heartbeat）の設計案（2026-09-13、実機不要）

Planning.md Phase 1 作業項目8 の通信断試験で出た**新規の設計要求**に対する設計案。
**実装済み（2026-09-13）。** 実装結果は §9 を参照。

---

## 1. 何を解決するのか

2026-09-09 の実測で分かったこと:

> 走行中に操作PC側で `nmcli connection down g1-link` を実行しても、
> ロボットは **4.045 秒歩き続け、約 0.85m 前進した**。
> `sshd` が TCP 切断を 14 秒検知せず SIGHUP を出さなかったため、
> オンボードの指令プロセスが生き残って指令を送り続けた。

止まったのはクライアントが `--seconds 5` で有限時間に終わる設計だったからであり、
**通信断が止めたわけではない。対話的・無制限のクライアントなら歩き続けていた。**

### 既存の 3 層は、この穴を塞げない

| 層 | 検知するもの | 通信断で効くか |
|---|---|---|
| SDK 側 `duration` 満了（D-27、0.20秒） | 次の指令が来ないこと | ❌ 指令は来続ける |
| SDK 側 watchdog（D-09/D-10、`cmd_timeout` 0.30秒） | ROS 側プロセスの死亡・停止 | ❌ `cmd_router` は生きている |
| ROS 側 watchdog（`cmd_timeout`） | Nav2 の停止 | ❌ Nav2 も生きている |

**いずれも「オンボード側の誰かが死ぬこと」を検知する仕組み**である。
通信断では**オンボード側は全員無事**で、消えるのは操作PC だけなので、誰も気づかない。

Nav2 を載せると悪化する。`bt_navigator` は Goal を受け取ったら通信断とは無関係に
実行を続けるので、**操作PCが見えなくなっても巡回を完走しようとする。**

---

## 2. どこで監視するか

| 案 | 内容 | 評価 |
|---|---|---|
| **(A) `g1_cmd_router` で監視** | 操作PC の heartbeat を受け、途絶したらゼロ速度＋Nav2 Goal キャンセル | ✅ **これを推す。**「`cmd_router` は生きていて操作PCだけが消える」という当該ケースを、まさに `cmd_router` が検知できる |
| (B) SDK 側プロセスで監視 | IPC 経由で heartbeat を中継して SDK 側が判定 | D-09 の「watchdog は SDK 側」という原則には合うが、SDK 側は**ネットワークを持たない**ので `cmd_router` の中継が必須。中継が生きている限り (A) と等価で、層が増えるだけ |
| (C) 両方 | — | (B) の利点が薄いので過剰 |

**(A) を採ると、3 層が過不足なく揃う:**

| 消えたもの | 検知する層 | 実測済み |
|---|---|---|
| 操作PC（通信断） | **`cmd_router` の heartbeat 監視**（新規） | ❌ 未実装 |
| `cmd_router` / Nav2 | SDK 側 watchdog（`cmd_timeout` 0.30秒） | ✅ kill -9 で 0.79秒歩容終了 / 3.77秒静止 |
| SDK 側プロセス | `duration` 満了（0.20秒） | ✅ |

## 3. 何を運ぶか（transport）

⚠️ **TCP の切断検知に依存してはいけない。** 今回の事故の原因がまさにそれで、
`sshd` は 14 秒間切断に気づかなかった。ROS トピック（DDS）も、切断時の
discovery の振る舞いが読みにくいうえ、リンクが不安定なときに再接続で時間を食う。

**推奨: 素の UDP データグラムを固定周期で送る。**

```
操作PC                                    PC2
  heartbeat_sender  ──UDP:<port>──▶  g1_cmd_router
   （5Hz、seq と送信時刻を載せる）        受信時刻を記録
```

- **UDP なので「届かない」がそのまま「届かない」として現れる。** 再送もハンドシェイクも
  無いので、リンクが死ねば即座に受信が止まる
- `seq` を載せて、巻き戻り（古いパケットの遅延到着）を弾く
- 送信時刻も載せるが、**判定には使わない**（PC 間の時刻同期を前提にしないため）。
  判定は PC2 側のローカル時計で測った「最後に受信してからの経過時間」で行う。
  時刻はログと遅延の可視化にのみ使う

---

## 4. 判定パラメータ（案）

| パラメータ | 案 | 根拠 |
|---|---|---|
| 送信周期 | **5 Hz**（200ms） | 指令の 20Hz より粗くてよい。UDP なので取りこぼしを前提に余裕を持つ |
| `operator_timeout_s` | **1.0 秒** | 5 回連続で落ちたら異常と見なす。実測の「切断後 0.85m 前進」に対し、1.0秒で検知すれば追加の前進は 0.3m 弱に収まる計算（`max_vx=0.30`） |
| 起動時の猶予 | **heartbeat を一度も受けていない間は NAVIGATING を許可しない** | 「送信側を立ち上げ忘れたまま巡回を始めてしまう」を防ぐ |

⚠️ `operator_timeout_s` を短くしすぎると、Wi-Fi の瞬断で巡回が止まる。
**実運用の電波状況を測ってから決めるべき値**なので、パラメータにして実機で詰める。

## 5. 途絶したら何をするか

3 つに分けて考える必要がある。

1. **速度をゼロにする** — 異論なし
2. **Nav2 の Goal をキャンセルする** — しないと、リンク復旧時に
   `bt_navigator` が中断地点から勝手に再開する。**キャンセルすべき**
3. **どの状態へ遷移するか** — `FAULT` か `E_STOP` か

`E_STOP` は手動解除が必須（`ClearEStop()` は `STANDBY` へ戻すだけ）。
リンクが瞬断するたびに人が現地へ行く必要が出るので、**`FAULT` が妥当**。
`FAULT` なら `/g1/clear_fault` で遠隔復帰できる。

⚠️ ただし `FAULT` からの復帰は「操作PCが戻ってきた」だけで自動に行ってはいけない。
**人が明示的に `clear_fault` を叩くこと**で、無人の自動再開を防ぐ。

## 6. ✅ 決定: 通信断では巡回を停止する（2026-09-13、ユーザー確認済み・D-31）

運用方針の選択だったので確認した。**(a) 止める** に決定。

| 方針 | メリット | デメリット |
|---|---|---|
| **(a) 止める**（本設計案の前提） | 人が見ていない状態でロボットが動き続けない。通信断＝監視不能なので、事故時に誰も気づけない | 自律巡回の意味が薄れる。Wi-Fi の弱い場所で巡回が中断し続ける可能性 |
| (b) 止めない（ログのみ） | 電波の届かない区画も巡回できる。自律性が高い | **実測で証明された穴がそのまま残る。** 暴走時に遠隔から止める手段がない（純正リモコンの電波が届く範囲に限られる） |
| (c) 速度を落として継続 | 妥協案。低速なら被害が小さい | 「安全な速度」の根拠が無い。`min_vx=0.25` を下回ると歩容自体が成立しない（U-12）ので、**そもそも減速の余地がほとんど無い** |

📌 **(c) は U-12 の実測により実質的に選べない。** G1 は `vx=0.2` で進行方向が
定まらなくなるため、「ゆっくり歩いて帰る」という選択肢が物理的に存在しない。

**理由**: 警備 PoC の目的が「異常を見つけて人に知らせること」である以上、
人と繋がっていない状態で動き続けることに価値が無いため。

⚠️ **残る未決**（QUESTIONS.md Q12）: `operator_timeout_s` の初期値（案 1.0 秒、
会場の電波状況に依存するので実機で詰める）と、遷移先を `FAULT` にするか。
どちらも暫定値で実装を進められる。

## 7. 受入試験（実機必須）

2026-09-09 と同じ手順で再現して、数値が改善することを確認する。

```bash
# 操作PC 側
# ① heartbeat 送信を開始してから Goal を送る
# ② 走行中に切断する
nmcli connection down g1-link
```

| 確認項目 | 2026-09-09 の実測 | 目標 |
|---|---|---|
| 最後に歩容が観測された時刻 | t=+4.045 秒 | **t=+1.5 秒以内** |
| 切断後の前進距離 | 約 0.85 m | **0.35m 以内** |
| Nav2 Goal | 実行され続けた | キャンセルされている |
| 状態 | `NAVIGATING` のまま | `FAULT` |
| リンク復旧後 | プロセスが残っていた | 自動再開しない。`clear_fault` が必要 |

⚠️ **この試験は「ケーブルを抜けば止まる」ことの確認ではない。**
物理的な停止手段（純正リモコン）が唯一の最終防衛線であることは変わらない（§7）。
heartbeat は**被害を小さくする仕組みであって、停止手段ではない。**

## 8. 実装の見積もり

| 作業 | 規模 |
|---|---|
| `heartbeat_sender`（操作PC 側、UDP 送信のみ） | 小。ROS 非依存で書ける |
| `g1_cmd_router` に UDP 受信スレッドと判定を追加 | 中。既存の `ReconnectLoop` と同じ形の別スレッド |
| `SafetyManager` に `OnOperatorLost()` を追加 | 小。`OnTfStale()` 等と同じく `TransitionFault()` を呼ぶだけ |
| Nav2 Goal のキャンセル | 中。`cmd_router` は現在 Nav2 の action client を持っていない。`/g1/stop` の TODO（「Nav2 Goal のキャンセル自体は上位の責務」）と同じ課題 |

📌 **Goal キャンセルだけ既存の宿題と重なっている。** `OnStop()` のコメントに
「Nav2 Goal のキャンセル自体は上位(mission/bringup層、未実装)の責務」とあり、
heartbeat 途絶時も同じ経路が要る。**まとめて設計したほうがよい。**

### 検証結果（モック SDK、Humble コンテナ）

| # | シナリオ | 結果 |
|---|---|---|

単体テスト 54 件が全て通過（heartbeat 関連で 15 件追加）。

### 🐛 実装中に踏んだバグ 2 件

どちらも単体テスト・統合試験で見つかった。**設計段階では想定していなかった。**

**1. `SO_REUSEADDR` で同じポートに二重 bind できてしまう**

Linux では UDP に `SO_REUSEADDR` を付けると同じ `addr:port` に複数の socket が
bind できる。`cmd_router` を誤って二重起動すると datagram が両者に振り分けられ、
**どちらも「取りこぼしている」＝途絶したと誤検知する。**
TIME_WAIT の回避は TCP の話なので受信専用 UDP に付ける利点は無く、削除した。
二重 bind は `EADDRINUSE` で失敗し、起動時に気づける。

**2. 送信プログラムを再起動すると永久に拒否される**

`seq` の単調性チェック（遅れて届いた古いパケットで「生きている」と誤認しないため）
が、送信側の再起動で `seq` が 1 に戻ったときも効いてしまい、**新しいパケットを
すべて古いものとして拒否し続けた。** 運用で送信を再起動したらロボットが二度と
動けなくなる。**起動ごとに振り直すセッション ID**（乱数 64bit）をパケットに追加し、
session が変われば seq を追い直すようにした。単調性チェックはセッション内で維持。
