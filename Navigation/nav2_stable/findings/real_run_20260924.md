# 2026-09-24 実機セッション（Sorasta）— 歩いたが、costmap の衝突判定で止まる

会場を Sorasta に移して初めての実機 Nav2。**機体は Nav2 の指令で 2 回歩いた**が、
どちらも数秒で `collision ahead` により停止した。**今日いちばん大きい収穫は、
実機でしか出ない不具合を 3 件潰したこと**と、**16分問題の切り分けが進んだこと**。

---

## 1. 潰した不具合（3件・いずれも実機で初めて出た）

### ① `patrol_waypoints:=`（空の引数）で Nav2 が起動すらしない

巡回路を渡さない**通常運用**で、`ros2 launch` が
`malformed launch argument 'patrol_waypoints:='` を出して**起動前に落ちていた**。
`g1up.sh` からは「§5 の自動校正が終わらない」に見え、原因が 1 行のログにしか出ない。

→ `start_nav.sh` で**空なら引数ごと渡さない**ようにした。

### ② Nav2 が二重に立ち、lifecycle が半分だけ active になる

`g1up.sh` は §5 で 1 回、§7b（map→odom 適用）でもう 1 回 `start_nav.sh` を呼ぶ。
**前を落としていなかったので必ず 2 本立つ。** `lifecycle_manager` が 2 つになって
ノード名が衝突し、

| active だったもの | unconfigured のまま |
|---|---|
| controller_server / behavior_server / velocity_smoother | **map_server / planner_server / bt_navigator** |

という中途半端な状態になる（Goal を投げても計画が出ない）。

→ `start_nav.sh` の冒頭で**前の Nav2 を必ず落とす**ようにした。

⚠️ **`ros2 lifecycle get` 自体が嘘をつくことがある。** 最初の確認で全ノードが
`xmlrpc.client.Fault: !rclpy.ok()` を返し、「全部死んでいる」ように見えた。
**`ros2 daemon stop` を挟むと正しい状態が出る。** 検収が転んだら、まず daemon を疑うこと。

### ③ ⚠️⚠️ 内蔵SLAM の時計が PC2 から離れていく（**今日いちばんの発見**）

記録中の `/tf` で実測（PC2 の受信時刻 − ヘッダの時刻）:

| | |
|---|---|
| ずれ | **+5.0 秒**（ヘッダのほうが過去） |
| 20 秒あたりの拡大 | **+0.06 秒（≒0.3%）** |

伝送遅延なら一定のはずなので、これは**時計のドリフト**。`/dog_odom` と IMU は
PC2 の時計と一致している（9/23 の記録で受信−ヘッダ = +0.000 秒）ので、
**ずれているのは内蔵SLAM（dock）だけ**。

`g1_cmd_router` は PC2 の時計で `now − 0.5秒` の TF を要求するため、
**TF が永久に `stale`（`Lookup would require extrapolation into the future`）→
`STANDBY` から一生上がらない。**

→ `g1_slam_odom_tf.py` に **`--restamp-now`（既定 ON）** を足し、TF と `/odom` を
**PC2 の時計で打ち直す**ようにした。ずれの大きさは 30 秒ごとにログへ出す。

📌 **「SLAM が落ちたら FAULT」は壊れない。** 中継は odom を受けたときだけ動くので、
配信が止まれば TF も止まる（タイマーではない）。
⚠️ 代償: 実際の伝送遅延ぶんだけ姿勢が新しく見える。

## 3. 16分問題（HANDOVER ③）— **「時間で切れる」が濃厚になった**

**このセッションで `1801` は 1 回しか送っていない**（再起動時も再送しない作り）。

| | |
|---|---|
| 起動 | 07:22:45 |
| 最後に生存 | 07:40:13 |
| 停止 | **07:41:22 → 寿命 18.5 分** |

⚠️ **この間、他の人が機体を歩かせていた時間が含まれる**（odom が 0.6m 以上動いた）。
**歩いていても 18.5 分で切れた**ので、「**無動作で切れる**」説は弱まった。

⚠️ ただし **n=1**。過去 3 回（15.7〜17.0 分）より長いのも説明できていない。

止まり方は設計どおり: TF 途絶 → `g1_cmd_router` が STANDBY → **指令は 1 件も
SDK に通らない**。復帰は `1801` 再送 → **§7 の地図照合やり直し**（odom 原点が戻るため）。

## 4. `cmd_timeout` を 0.30 → **1.0 秒**にした（利用者の判断）

`navigation.launch.py` に `cmd_timeout` 引数を足し、既定を **1.0** にした。

📌 **機体が止まる速さは変わらない。** systemd 側の `--cmd-timeout 0.30` は据え置きなので、
指令が途切れれば**機体は 0.3 秒でゼロ速度**になる。伸ばしたのは
「**FAULT にして Goal ごと捨てるまでの猶予**」だけ。

効果はあった（0.30 のときは復帰動作に入った直後に落ちたが、1.0 では**5 秒間走り続けた**）。
**ただし止まる根本原因は別だった** → §5。

## 5. ⚠️ 残った壁: `collision ahead` で controller が指令を出さなくなる

2 回目の Goal の 10 秒間:

```
+0.0s  Goal 受理 (-0.02,0.11) → (0.25,1.29)
+0〜5s 機体が歩く（odom で 0.62m）
+5.0s  RegulatedPurePursuitController detected collision ahead!  ← 連続
+5.3s  Controller patience exceeded → follow_path abort → local_costmap 全消去 → 再試行 → また collision
+9.5s  abort の間に指令が 1 秒以上途切れて cmd_timeout → FAULT → Goal 取り消し
```

**`cmd_timeout` をさらに伸ばしても解決しない**（機体が動かない時間が延びるだけ）。

原因の候補は 2 つ。**まだ切り分けていない**:

| | 内容 | 確かめ方 |
|---|---|---|
| (1) 実在の障害物 | 人・椅子。当日、機体の周囲に複数人がいた | 周囲 2m を空けて再試行する（1分） |
| (2) **地図の粒状ノイズ** | 今日の地図は `/dog_odom` 由来で occupied が点状に散る（[map_from_dog_odom_20260923.md](map_from_dog_odom_20260923.md)）。経路上に乗れば RPP は「衝突」と見る | 記録を再生して local/global costmap を見る |
