# map_localizer の照合1回の所要時間と、実機で歩かせた結果（2026-11-03）

## 結論

**`--match-rate` は既定の 2Hz のままにする。** PC2 では照合1回が p95 で 81ms で、
2Hz なら 1コアの約 15% しか使わない。CPU を理由に下げる必要も、上げられない理由も無い。
上げるかどうかは、**旋回中にずれがどれだけの速さで増えるか**（実機で歩かせる計測）を見てから決める。

それまで 2Hz には根拠が無かった（2026-09-13 の初版からの値で、計測の記録が無い）。

## 測り方

`tools/bench_localizer.sh` で、記録済み bag を再生して `map_localizer.py --observe-only` を動かし、
`--timing-csv` で照合1回ごとの時間を残した。**機体は動かさない。**
`ROS_DOMAIN_ID=77`＋`ROS_LOCALHOST_ONLY=1` で閉じたので、機体の電源が入っていても混ざらない。

- bag: `0911_robag` から3トピック（点群・IMU・内蔵SLAM の odom）の先頭 180 秒を抜いたもの（752MB）
- 地図: `room_a_map_20260911_edited.yaml`、初期 map→odom は `-0.30 0 0`
  （`find_map_offset.py --yaw-range 180` で求めた。50cm以内 100%）
- 120 秒再生、`--match-rate 10`（点群をほぼ全部照合させて標本を増やすため）

```bash
bash tools/bench_localizer.sh bench/bench_0911_180s maps/grids/room_a_map_20260911_edited.yaml -0.30 0 0 120 10 <出力dir>
```

## 結果

| 所要時間 [ms] | PC2（Orin NX, 8コア, pixi Humble） | | | 操作PC（i7-13620H, Docker） | | |
|---|---|---|---|---|---|---|
| | 中央値 | p95 | 最大 | 中央値 | p95 | 最大 |
| 点群の変換 | 4.8 | 7.0 | 30.2 | 3.1 | 4.7 | 8.0 |
| 照合 | 65.2 | 74.6 | 85.0 | 24.2 | 40.6 | 79.0 |
| **合計** | **70.5** | **81.0** | 93.3 | 27.5 | 44.8 | 84.7 |

- PC2 は照合 692 回。スコアは中央値 0.05m、441 回採用（条件が正しく動いていた）
- 点数は**毎回上限の 1500 点で頭打ち**。計算量は場所によらず、ほぼ「候補 468 個 × 1500 点」で決まる
- p95 から見た上限は PC2 で **約 12Hz**（照合だけに CPU を使えた場合）
- 実効が 6Hz になっているのは、間引きが「点群の到着間隔（約 0.103 秒）と 1/rate の比較」で
  決まるため。計算が追いつかなかったのではない

## 頻度ごとの目安（PC2）

| `--match-rate` | 1コアの使用率 | 照合の間に溜まるずれ |
|---|---|---|
| 1Hz | 約 7% | 1 秒ぶん |
| **2Hz（既定）** | **約 15%** | 0.5 秒ぶん |
| 5Hz | 約 35% | 0.2 秒ぶん |

⚠️ ノードは1スレッドなので、**照合している間（最大 約 90ms）は 20Hz の TF 配信も止まる**。
頻度を上げると TF の間隔が乱れやすくなる。

## 無線運用との関係

照合の入力（点群・odom）は G1 本体→PC2 の内部有線で届き、照合も PC2 で完結するので、
**操作PC が有線でも無線でも所要時間は変わらない。** ただし操作PC の RViz が無線越しに点群を
購読すると、PC2 が送出に CPU を使うので、その分は照合と取り合う可能性がある（未計測）。

## 実機で歩かせた結果（同日、room_a、リモコンで手動）

記録: PC2 `~/g1_nav2/runs/drift_20261103_121811/`（点群・IMU・内蔵SLAM の odom・TF、707 秒）。
床の印から出発し、直進往復（b）、その場で左右に2周ずつ（c）を2回行い、毎回印に戻した。
旋回は平均 52°/s、最大 66°/s、合計で左右それぞれ約 2,040°。

### 内蔵 SLAM の odom はほとんどずれなかった

印の上で止まっていた区間の点群（odom 系）を、最初の静止区間の点群に 2D 照合した
（odom が正しければぴったり重なる。地図を使わずに測れる）:

| 区間 | odom の向き | 重ねるのに要る補正（= odom のずれ） | 10cm 以内 |
|---|---|---|---|
| b のあと | +23.3° | 0.05m / 0.10° | 94% |
| c 1回目のあと | -4.3° | 0.06m / 0.30° | 98% |
| c 2回目のあと | +16.3° | 0.02m / 0.10° | 96% |

- **約 4,000° 回っても 6cm / 0.3° 以内。** 9/25 の 10.8m は再現しなかった
- odom の向きが +23° → -4° → +16° と変わったのは**実際に機体の向きがそれだけ違った**から
  （人が目で印に合わせると ±20° ばらつく）。⚠️ **向きのずれを目視で測ってはいけない**

### 照合が全部棄却されていた原因: 機体自身の体を見ていた

現場では `find_map_offset.py` の一致率が 20〜30% で「失敗」に見え、
`map_localizer.py` も照合をほぼ全部棄却した（スコア中央値 0.43m > `--max-score 0.35`）。
しかし記録全体の点群をまとめて照合すると、**現場の答えは正しかった**（10/21 と 9/11 の
2枚の地図で、現場と同じ値。10/21 の地図で map→odom = (-0.76, +3.46, 218°)、50cm 以内 81%）。

1フレームの点群（高さで絞ったあと）を機体からの距離で分けると:

| 機体からの距離 | 点の割合 | 壁から 20cm 以内 |
|---|---|---|
| 0〜0.5m | **69%** | 14% |
| 0.5〜2m | 2% | 20〜64% |
| 2m〜 | 29% | **84〜95%** |

**MID-360 が機体自身の腕や胴を拾い、それが点の 7 割を占めていた。** スコアの付け方
（平均・上限付き平均・inlier 率）を変えても採用率は 11% 前後のままで、原因はスコアではなかった。

→ `map_localizer.py` と `find_map_offset.py` に **`--min-range`（既定 1.0m）** を入れた。

| | 修正前 | 修正後 |
|---|---|---|
| `find_map_offset.py`（印の上） | 20cm 以内 29% / 50cm 以内 32% | **90% / 99%**（答えは同じ） |
| `map_localizer.py`（PC2 で記録を再生、600 秒） | 採用 0 回 | **採用 1,125 / 棄却 29（97.5%）** |

修正後の `map_localizer.py` の累積補正（odom がほぼ正しいので 0 付近が正しい）:
止まると 0.1m / 0.5° 以内に戻る。**ただし旋回中は一時的に 0.22m / 5.25° まで動く**
（52°/s では 1 フレーム 0.1 秒の間に約 5° 回り、点群が流れるためと見られる）。
`correct` で使うと、そのぶん旋回中に位置が飛ぶ。旋回中（20°/s 超）は照合を休ませると、
記録の再現で向きの最大誤差が 5.75° → 2.75° になった（未実装）。
