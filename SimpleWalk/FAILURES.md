# 実機操作 失敗ログ

実機G1を動かす際に実際に起きた失敗と、その原因・反省・再発防止策を記録する。
`CLAUDE.md`（手順・環境情報）とは別に、**同じ失敗を繰り返さないための記録**として維持する。
新しい失敗が起きたら、下のテンプレートに沿って追記する。

## テンプレート

```
## YYYY-MM-DD: 失敗の一言タイトル

**何が起きたか**
（観測された事実。憶測ではなく実際に見えたことを書く）

**原因**
（コード上・手順上の根本原因）

**反省**
（なぜ事前に気づけなかったか。見落としていた前提は何か）

**再発防止策**
（実際にコード/手順をどう変えたか）
```

## 2026-08-21: 前進後にdisconnect()で脱力し、支えの無い状態で転倒

**何が起きたか**
`walk_forward_real.py`で前進コマンドを送って歩行させた後、スクリプトが
終了処理として`robot.disconnect()`を呼んだ瞬間、G1が脱力し、支えていなかったため
その場で崩れて倒れた。

**原因**
`UnitreeG1.disconnect()`は実機の場合、内部で`_send_zero_torque()`を呼び、
**全関節をゼロトルク（脱力）にしてから切断する**仕様になっている
（`unitree_g1.py`のdocstring: "Put robot in passive mode"）。
`walk_forward_real.py`は前進コマンド送信直後、1秒だけ待機コマンドを送ってから
無条件に`disconnect()`を呼んでいたため、**人間が支える準備をする間もなく脱力が発生した**。

**反省**
歩行を開始する前（`connect()`直後）には「安定して自立していることを目視確認してから
進める」という確認ゲートを設けていたが、**歩行を終える側（`disconnect()`前）には
同様のゲートを設けていなかった**。「動き出す前は危険、動き終わったら安全」という
思い込みがあり、脱力という状態遷移自体が転倒リスクになることを見落としていた。
disconnect()の実装（ゼロトルクにする仕様）を把握していたにもかかわらず、
スクリプトの終了処理に反映し忘れていた。

**再発防止策**
`walk_forward_real.py`に`hold_standing_until()`を追加。前進コマンド終了後は
disconnect()を呼ぶ前に、待機コマンド（remote.*ゼロ）を50Hzで送り続けるスレッドを
立てて**その場で直立姿勢を保持し続け**、人間が「支える準備ができた」とEnterで
明示的に確認するまでdisconnect()（脱力）を実行しないよう変更した。

→ 教訓として一般化すると: **ロボットの制御状態が変わる遷移（脱力・モード切替・
制御開始/終了）は、動作の開始時だけでなく終了時にも同じ重みで安全確認するべき。**
