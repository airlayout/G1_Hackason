# 失敗ログ

このフォルダでの開発中に実際に起きた失敗と、その原因・反省・再発防止策を記録する。
新しい失敗が起きたら、下のテンプレートに沿って追記する。

## テンプレート

```
## YYYY-MM-DD: 失敗の一言タイトル

**何が起きたか**
（観測された事実。憶測ではなく実際に見えたことを書く）

**原因**
（コード上・手順上の根本原因）

**反省**
（なぜ事前に気づけなかったか。見落としていた前提は何か）

**再発防止策**
（実際にコード/手順をどう変えたか）
```

## 2026-11-13: 160ms 単位のマイク受信を途切れと判定し、発話が確定しなかった

**何が起きたか**
G1 内蔵マイクの受信と生存監視は正常で、発話時に音量も上がったが、
常時待受から判定記録が作られず、ツールも呼び出されなかった。

**原因**
マイクの UDP パケットは 16 kHz の 2560 サンプル（160ms）を含む。
`ContinuousListener.feed` はパケット到着間隔が 100ms を超えるだけで区間検出を
リセットしていたため、通常受信でも発話を連結できなかった。

**反省**
受信と音量表示が正常なことだけでは、発話区間が完成することを確認できない。
短いフレームでの試験だけでは、実際のパケット単位での不具合を検出できなかった。

**再発防止策**
到着間隔から現在のパケットが含む音声時間を差し引き、残った空白が 100ms を
超えた場合にリセットする。160ms 単位の連続受信で発話を確定する試験と、
160ms 分のパケット欠落では部分発話を破棄する試験を追加した。

## 2026-11-13: 手振りの登録音声と未登録の言い換えでは判定結果が異なった

**何が起きたか**
合成音声の「手を振って」を登録し、別の「手を振ってください」を実モデルに入力すると、
手振り 0.955・見送り 0.892、差 0.063 で `min_margin=0.08` を満たさず見送られた。
肯定の登録例を 2 種類に増やしても、未登録の「手を振って挨拶して」は差 0.052 で見送られた。
登録音声の再生では音量による区間抽出 → `wave_hand` → dry-run まで通った。

**原因**
この検証では肯定・否定の音声同士にも高い類似度があり、言い換えで余裕が小さくなった。
登録音声と入力音声の一致だけで、未登録の文言への一般化は確認できない。

**反省**
SDK への実行経路が正しくても、音声分類の精度は別に評価する必要がある。

**再発防止策**
しきい値は緩めず、手振り用の音声設定例に肯定 2 種類・否定・雑談を用意した。
実録音と登録に使っていない録音での検証を実行手順に記載し、曖昧な場合は引き続き見送る。

## 2026-11-13: 日本語音声と説明文の類似度だけでは肯定・否定を分離できなかった

**何が起きたか**
日本語の合成音声によるボトル押し・下ボタン押し・否定・挨拶の 4 例で、説明文との照合を試した。
有効な 2 指示も `no_action` の説明文が最高スコアとなり、2 位との差が小さいため `ambiguous` で見送られた。

**原因**
この検証例では、肯定の音声と否定の説明文にも高い類似度が出た。
埋め込みの近さだけで肯定・否定を区別できるとは限らず、見送り用説明文を増やすだけでも解決しなかった。

**反省**
モデルが音声・文章を同じ空間に埋め込めることと、ロボット指示を十分な精度で分類できることを
分けて検証する必要があった。

**再発防止策**
音声の登録例同士で比較する `reference_audio` も指定できるようにした。
しきい値は未校正と明記し、登録音声と異なる検証音声による評価が必要なことを README に追記した。
曖昧なときは実行を見送り、dry-run を既定にする。

## 2026-11-13: 音声入力でも AutoProcessor が torchvision を要求した

**何が起きたか**
EmbeddingGemma 2 の音声ベクトル生成を実モデルで試すと、AutoProcessor の読み込み時に
`EmbeddingGemma2VideoProcessor requires the Torchvision library` で終了した。

**原因**
Transformers 5.22.2 の AutoProcessor は、音声だけを使う場合もモデルの設定に従って
画像・動画用 processor を構築する。画像エンコーダの重みを省略しても、この依存は残る。

**反省**
モデルの重みの依存と、前処理クラスを構築するための依存を分けて確認できていなかった。

**再発防止策**
requirements に torchvision を明記した。実モデルでの `--embed-only` による動作確認を行う。

## 2026-09-05: マイクの自動待ち受け(listen)が空文字を返す

**何が起きたか**
マイクmulticastを自動でON/OFFしながら待ち受ける方式（`listen`）では、
文字起こし結果が空文字になることがあった。

**原因**
未特定（GUIで明示的に録音区間を区切る方式では成功しているため、自動検出の
区間切り出しに問題がある可能性が高い）。

**反省**
自動化を優先して検証を急いだため、根本原因の切り分けが未完了のまま。

**再発防止策**
当面はGUI方式（赤=録音中の表示でON/OFFを人間が操作）を使う。自動`listen`は
使わない。

## 2026-09-05: マイクGUIと対話パイプラインが同一multicastを奪い合う

**何が起きたか**
マイク文字化GUI（`g1_mic_transcribe.py gui`）と対話パイプラインを同時に動かすと、
同じマイクmulticastストリームを両方が受信しようとして競合した。

**原因**
G1のマイクmulticastは1系統しかなく、複数プロセスから同時に読むことを
想定していない。

**再発防止策**
どちらか片方だけを起動する運用にする。同時起動しない。

## 2026-09-05: ElevenLabs TTSが絵文字のみの文でクラッシュ（`input_text_empty`）

**何が起きたか**
LLMの応答が絵文字のみの文だった場合、ElevenLabs側のTTS APIが
`input_text_empty`エラーを返し、対話パイプラインが停止した。

**原因**
LLM出力のテキストをそのままTTSに渡していたため、TTS側が「空文字」とみなす
入力（絵文字のみ等）が素通りしていた。system promptで絵文字禁止を指示しても
LLMが完全に守るとは限らない。

**反省**
入力側（system prompt）だけで制御しようとし、出力側（TTSに渡す直前）での
検証・サニタイズを怠っていた。

**再発防止策**
TTSへ渡す直前にテキストをサニタイズする関数（空文字・絵文字のみの場合は
そのターンのTTS呼び出し自体をスキップ）を追加。
